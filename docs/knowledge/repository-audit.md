# Repository Audit

审计日期：2026-08-04

范围：源码、测试、依赖、Git、README、Rules、Spec、Plan、Tasks 和 Knowledge。未读取 `.env` 内容，未调用真实上游服务。

## Summary

项目规模小、依赖方向清晰，HTTP 错误路径测试较完整，密钥与真实网络测试边界明确。主要缺口是 Python 环境入口不一致、工程门禁尚未自动化，以及生产安全、可观测性和性能基线均未建立。

## Findings

### P0: Python 环境不可复现且全局依赖不一致

- 证据：当前 Shell 的 `/usr/bin/python3` 为 3.9.6 且无法导入 FastAPI；`/Users/wangfei/anaconda3/bin/python3` 为 3.11.5，项目测试可运行，但 `pip check` 报告多项 Anaconda 全局包缺失或版本冲突。Pydantic 的导入版本显示 1.10.19，而包依赖检查还报告 2.12.5 元数据，说明共享环境存在不一致。
- 影响：README 和规则中的裸 `python3` 命令可能在新终端直接失败；共享全局环境无法作为可靠依赖基线，未来安装或升级可能产生非项目回归。
- 建议：确认团队环境管理方案，优先建立仓库本地 Python 3.11 `.venv`，从 `requirements.txt` 干净安装并重新运行 `pip check`；确认后更新 README 和所有命令入口。

### P1: 没有自动化 CI 质量门禁

- 证据：仓库不存在 GitHub Actions、GitLab CI 或其他 CI 配置。
- 影响：测试、依赖和 Markdown 检查依赖人工执行，合入质量不可强制保证。
- 建议：确认托管平台后创建 Spec，至少自动执行 Python 版本校验、依赖安装、全量测试、语法检查和 `git diff --check`。

### P1: 没有 Formatter、Lint 和类型检查配置

- 证据：不存在 `pyproject.toml`、Ruff、Black、Flake8、Mypy 或对应命令。
- 影响：代码风格与部分静态缺陷只能依赖人工审查。
- 建议：先评估 Ruff 或现有团队工具，不在未确认前增加依赖；若引入，应记录版本、配置和 CI 门禁。

### P1: 生产访问控制与滥用保护缺失

- 证据：路由无认证授权、CORS、限流或请求体大小策略。
- 影响：若服务暴露到非可信网络，调用方可能消耗模型额度或扩大上游风险。
- 建议：在确定部署边界和调用方后创建安全 Spec；本地学习用途则明确限制为非生产。

### P1: 可观测性与正式健康检查缺失

- 证据：无业务日志、Request ID、Tracing、指标、告警或 Readiness/Liveness；`GET /` 仅返回示例 JSON。
- 影响：生产故障难以关联请求、定位上游耗时和判断服务就绪状态。
- 建议：先确认 `GET /` 定位和部署平台，再设计最小日志、请求标识和健康检查；不得把当前根路由描述为正式健康检查。

### P2: 依赖可复现性有限

- 证据：依赖版本已精确固定，但没有 lock 文件或哈希校验，也没有供应链扫描。
- 影响：跨平台安装仍可能受间接依赖和包源变化影响。
- 建议：结合团队 Python 工具链确认锁定方案与依赖安全检查，不为本 Demo 单独强加工具。

### P2: 没有可靠性策略

- 证据：已设置连接和总超时并分类错误；没有重试、退避、熔断或降级。
- 影响：瞬时上游故障会直接失败；盲目增加重试又可能放大费用与延迟。
- 建议：先收集失败类型和幂等事实，再决定是否增加受控重试；当前保持无重试是明确现状，不属于实现错误。

### P2: 待建立性能基线

- 证据：不存在压测脚本和吞吐、平均延迟、P95/P99、失败率数据。
- 影响：无法量化超时、并发或连接管理变更的收益与风险。
- 建议：需要生产化或并发优化时，先建立可重复的本地/测试环境基线；不得编造目标。

### P2: 历史文档存在已被后续变更取代的描述

- 证据：早期阿里云接入 Spec 和 Tasks 描述逻辑位于 `main.py`，后续重构 Spec 已将其迁移到 Router 和 Service。
- 影响：不区分历史 Spec 与当前 Knowledge 时，AI 可能加载过期结构。
- 建议：保留历史文档不篡改；通过 Spec 索引标注时间顺序，并以当前 Knowledge 作为现状来源。

### P3: 测试分类和覆盖率门槛未定义

- 证据：当前 17 个测试集中在 `tests/test_chat.py`，没有覆盖率配置或 Integration/E2E 分类。
- 影响：随项目增长，测试职责可能混杂，覆盖缺口难量化。
- 建议：当前规模无需空壳分层；出现第二个领域或真实集成环境后再拆分测试类别并评估覆盖率门槛。

## Confirmed Strengths

- 依赖方向清晰，没有循环依赖或空壳数据层。
- 输入使用 Pydantic 严格校验。
- 外部 HTTP 调用异步且有显式超时。
- 上游错误体和密钥不直接暴露。
- 自动化测试通过 MockTransport 隔离真实网络，覆盖成功、边界、超时、连接、鉴权和非 JSON。
- `.gitignore` 覆盖 `.env`、Python 和 Pytest 缓存。
- Git 提交历史已采用清晰的 Conventional Commit 风格。
