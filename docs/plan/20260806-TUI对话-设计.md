- 状态：已批准

## 2. 当前事实

当前项目只有 HTTP 入口：

```text
main.py
  -> app.application
       -> app.routers.chat
            -> app.services.aliyun_responses
```

- `POST /chat` 使用 Pydantic 校验非空严格字符串。
- Router 调用 `request_upstream_response()`，成功时原样透传上游状态码和 JSON。
- Service 当前直接抛出 FastAPI `HTTPException`，因此无法被非 HTTP 界面自然复用。
- 上游地址、模型 `qwen3-max`、连接超时 10 秒和总超时 60 秒已经固定。
- 自动化测试通过 HTTPX `MockTransport` 隔离真实网络。
- 仓库尚未安装 TUI 框架，也没有共享用例层或会话状态。

主要结构问题不是缺少更复杂的 Agent 框架，而是现有 Service 把上游调用和 HTTP 错误表现绑定在一起。

## 3. Reasonix 原则的取舍

采用 Reasonix 中适合当前项目的两条原则：

1. 多个交互界面共用同一运行内核。
2. 界面层只负责输入、展示和交互状态，不复制 Provider 调用逻辑。

不复制 Reasonix 的工具系统、权限审批、Sandbox、Plan、多 Agent、Plugin、MCP、持久化会话或流式事件系统。这些能力在当前仓库没有真实需求和底层实现。

映射关系：

| Reasonix 思路 | 当前项目落地 |
| --- | --- |
| 多界面共享 Engine | FastAPI Router 与 Textual TUI 共享 Chat Runtime |
| 界面保持轻薄 | TUI 只处理编辑、命令、状态、显示和取消 |
| Provider 位于内核下游 | 阿里云 Responses Service 仍唯一负责 HTTPX 调用 |
| 依赖方向清晰 | `surface -> runtime -> service`，禁止 HTTP/TUI 互相调用 |

## 4. 依赖决策

在 `requirements.txt` 增加并固定：

```text
python-dotenv==1.2.2
textual==8.2.8
```

- Textual 8.2.8 支持 Python 3.11，提供 `TextArea`、`RichLog`、Worker 和无头测试能力。
- python-dotenv 1.2.2 支持 Python 3.11，只用于独立 TUI 入口加载项目根目录 `.env`。
- 不安装 `textual-dev`、语法高亮 extra 或 `pytest-asyncio`。
- 异步 TUI 测试在同步 Pytest 测试中使用 `asyncio.run()` 包装 `app.run_test()`，保持现有 `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` 门禁可用。
- 不升级任何现有依赖。

版本升级属于后续独立维护事项，不能在本需求实现中自动放宽版本范围。

## 5. 目标架构

```text
                     +--------------------------+
POST /chat ----------> FastAPI Router           |
                     | HTTP 校验和错误映射       |
                     +-------------+------------+
                                   |
                                   v
                     +--------------------------+
                     | Chat Runtime             |
                     | 单轮用例和中立错误语义    |
                     +-------------+------------+
                                   |
                                   v
                     +--------------------------+
                     | Aliyun Responses Service |
                     | HTTPX、鉴权、超时、JSON   |
                     +--------------------------+
                                   ^
                                   |
                     +-------------+------------+
python -m app.tui ---> Textual TUI              |
                     | 输入、状态、显示、取消    |
                     +--------------------------+
```

约束：

- `app.runtime` 不导入 FastAPI 或 Textual。
- `app.tui` 不导入 Router、FastAPI Application 或 `main.py`。
- Router 和 TUI 只调用 Runtime，不直接复制 Service 的调用与错误判断。
- Service 不导入 Runtime、Router 或 TUI，避免反向依赖和循环依赖。
- `main.py` 及 `main:app` 保持不变。

## 6. 模块与职责

### 6.1 `app/services/aliyun_responses.py`

保留：

- 上游 URL、模型和超时常量。
- API Key 读取、Header/Payload 构造。
- HTTPX 生命周期、请求和 JSON 解码。

调整：

- 不再创建 `HTTPException`。
- 定义仅描述 Provider 失败的异常：配置缺失、超时、连接失败、鉴权失败、其他状态失败和无效 JSON。
- 异常只携带安全消息和必要的上游状态码，不携带 Header、Key 或上游错误体。
- `request_upstream_response()` 的成功返回仍为 `(status_code, body)`，保持透传所需信息。

### 6.2 `app/runtime/chat.py`

新增界面无关的单轮用例入口：

```python
@dataclass(frozen=True)
class ChatResult:
    upstream_status: int
    body: Any

class ChatErrorCode(str, Enum):
    INVALID_INPUT = "invalid_input"
    CONFIGURATION = "configuration"
    TIMEOUT = "timeout"
    CONNECTION = "connection"
    AUTHENTICATION = "authentication"
    UPSTREAM = "upstream"
    INVALID_RESPONSE = "invalid_response"

class ChatRuntimeError(Exception):
    code: ChatErrorCode
    user_message: str
    upstream_status: int | None

async def run_chat(input_text: str) -> ChatResult:
    ...
```

职责：

- 防御性校验输入是非空字符串；HTTP 的正式 422 契约仍由 Pydantic 保证。
- 调用阿里云 Service。
- 把 Provider 异常转换为稳定、界面无关的 `ChatRuntimeError`。
- 返回结构化结果，不生成 HTTP Response，也不生成终端文本。

Runtime 不维护对话历史，不把界面中的历史发送给模型。每次调用仍是独立单轮请求。

### 6.3 `app/routers/chat.py`

- `ChatRequest` 及其现有校验保持不变。
- 改为调用 `run_chat()`。
- 将 `ChatRuntimeError` 映射为现有 `HTTPException` 状态码和 `detail`。
- 成功时继续用 `JSONResponse` 原样返回 `ChatResult.body` 和 `upstream_status`。

HTTP 回归映射：

| Runtime 错误 | HTTP 状态 | `detail` |
| --- | ---: | --- |
| `CONFIGURATION` | 503 | `Upstream API key is not configured` |
| `TIMEOUT` | 504 | `Upstream request timed out` |
| `CONNECTION` | 502 | `Unable to connect to upstream service` |
| `AUTHENTICATION` | 上游 401/403 | `Upstream authentication failed` |
| `UPSTREAM` | 上游状态码 | `Upstream service returned an error` |
| `INVALID_RESPONSE` | 502 | `Upstream service returned invalid JSON` |

现有请求 Schema、422 响应、成功 JSON、状态码和错误文本均不得变化。

### 6.4 `app/tui/state.py`

只定义界面确实需要的状态，不建立通用状态框架：

```python
class RunStatus(str, Enum):
    READY = "Ready"
    THINKING = "Thinking"
    ERROR = "Error"
```

消息不做持久化模型。`RichLog` 是首期唯一显示记录，`/clear` 直接清空它。

### 6.5 `app/tui/application.py`

定义 `ChatTuiApp`，构造函数接收可替换的异步 `chat_runner`；默认值为 `run_chat`。测试注入 Mock Runtime，不访问真实网络。

组件：

| 区域 | Textual 组件 | 职责 |
| --- | --- | --- |
| 标题 | `Static` | 显示项目名称，避免引入首期不需要的时钟或导航行为 |
| 对话记录 | `RichLog` | 顺序显示 User、Assistant、Error、System |
| 输入 | `TextArea` | 多行编辑，默认软换行 |
| 状态栏 | `Static` | Provider、Model、Key 配置状态和运行状态 |
| 快捷键提示 | `Footer` | 只展示 Send 和 Cancel/Exit 快捷操作，不提供帮助命令 |

使用 Rich `Text` 对象写入记录区，不把上游文本当 Rich markup 解析，避免响应内容注入终端样式标记。

### 6.6 `app/tui/__main__.py`

启动顺序：

1. 用 `Path(__file__).resolve()` 计算仓库根目录。
2. `load_dotenv(root / ".env", override=False)`。
3. 创建并运行 `ChatTuiApp`。

`override=False` 确保显式 Shell 环境变量优先于 `.env`。入口不读取或打印文件内容，不要求启动 Uvicorn。

## 7. 界面布局

```text
+------------------------------------------------------------------+
| FastAPI Agent TUI                                                |
+------------------------------------------------------------------+
| You                                                              |
| 你是谁？                                                         |
|                                                                  |
| Assistant                                                        |
| 我是……                                                           |
|                                                                  |
| Error                                                            |
| Upstream request timed out                                       |
+------------------------------------------------------------------+
| 输入区                                                           |
| Enter 发送；Esc 退出                                             |
+------------------------------------------------------------------+
| Aliyun | qwen3-max | Key: configured | Ready                     |
+------------------------------------------------------------------+
```

- 记录区占剩余空间并自动滚动到最新消息。
- 输入区使用固定的合理最小高度，可随终端宽度软换行。
- 小终端以可滚动和不崩溃为目标，不承诺特定像素或帧率。
- 首期不渲染 Markdown、代码高亮或流式光标。

## 8. 键盘与命令

### 8.1 编辑与提交

- `Enter`：提交整个输入区内容。
- `Esc`：取消运行中的请求并退出应用。
- `Enter` 与 `Esc` 注册为 App 级高优先级 Binding，确保输入区聚焦时仍由应用处理。
- 提交成功进入请求流程后清空输入区并恢复焦点。
- 空白输入不调用 Runtime，写入一条本地校验提示，状态保持可用。

启动入口在导入 Textual 前设置 `TEXTUAL_DISABLE_KITTY_KEY=1`，不启用项目不需要的 Kitty 扩展键盘协议，避免其“上报所有按键”模式干扰 macOS 中文 IME；中文直接在原输入框中编辑。

### 8.2 命令

只有去除首尾空白后完全匹配以下文本才作为本地命令：

- `/clear`：清空 `RichLog`，状态回到 `Ready`；请求运行中时拒绝执行，避免隐藏仍在执行的操作。
- `/quit`：无运行中请求时退出；有运行中请求时先取消 Worker，再退出。

不实现 `/help` 或 `/chat` 命令。`/help`、`/chat` 以及其他未识别文本都作为普通模型输入，不建立隐藏的命令路由。

### 8.3 `Esc`

- Worker 正在运行：取消当前 Worker，然后退出 TUI。
- 没有 Worker：直接退出 TUI。

## 9. 请求状态机

```text
                     成功
Ready ----提交----> Thinking --------> Ready
  ^                    |                 |
  |                    | 已知/未知错误   |
  |                    v                 |
  +----下一次提交----- Error <-----------+
  |                    |
  +------取消-----------+
```

规则：

- 初始状态通常为 `Ready`；若启动时未配置 Key，显示配置提示并置为 `Error`。
- `Thinking` 期间禁止第二次提交。
- 新的有效提交会把 `Error` 切换为 `Thinking`。
- 请求成功切换为 `Ready`；失败切换为 `Error`，但应用不退出。
- 取消切换为 `Ready`，已取消请求的结果不得写入记录区。

## 10. 异步执行与取消

提交过程使用 Textual async Worker，不在事件处理器中直接等待 HTTP 请求：

```text
Enter
  -> 校验/记录用户输入
  -> 状态设为 Thinking
  -> run_worker(coroutine, exclusive=True, exit_on_error=False)
  -> await chat_runner(text)
  -> 写入成功或安全错误
  -> 更新最终状态
```

- `exclusive=True` 和应用级活动 Worker 引用共同保证最多一个请求。
- `exit_on_error=False` 防止 Worker 的意外异常直接关闭 TUI。
- Runtime 已知错误显示 `user_message`；未知异常只显示通用 `Unexpected internal error`，不显示 traceback。
- `Worker.cancel()` 将取消传播到异步 HTTPX 调用；退出 App 时 Textual 也会清理绑定到 App 的 Worker。
- Worker 完成前检查取消状态/请求代次，防止取消与完成竞态写入陈旧结果。
- 不捕获并吞掉 `CancelledError`，确保 HTTPX Client 上下文能正常清理。

## 11. 响应显示

HTTP API 继续原样透传完整上游 JSON。TUI 采用确定性显示策略：

1. 顶层 `output_text` 是非空字符串时显示它。
2. 否则按顺序提取 `output[*].text`。
3. 否则按顺序提取 `output[*].content[*].text`。
4. 没有可识别文本时使用 `json.dumps(body, ensure_ascii=False, indent=2, default=str)` 显示完整响应。

提取函数只负责展示，不修改 Runtime 结果，也不把推断后的文本暴露为 HTTP 契约。多个文本片段以换行连接。上游返回合法但非字典 JSON 时直接格式化为可读 JSON。

## 12. 配置与安全

- API Key 只通过 `os.getenv("DASHSCOPE_API_KEY")` 读取。
- `.env` 只由 TUI 入口加载；HTTP 启动仍使用现有 `uvicorn --env-file .env`。
- 状态栏只显示 `Key: configured` 或 `Key: missing`。
- 错误对象、UI、测试断言和文档都不保存真实 Key。
- 不展示上游错误体、请求 Header、环境文件内容或内部堆栈。
- 自动化测试使用明显假 Key 和注入式 Mock，不调用真实付费接口。
- `.env` 继续保持在 `.gitignore` 中。

## 17. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Service 异常重构改变 `/chat` 契约 | 现有调用方回归 | 先锁定并全量运行现有 17 个测试 |
| Textual 事件循环被网络等待阻塞 | 界面卡死 | 统一使用 async Worker，不在事件处理器 await 长请求 |
| 取消与响应完成竞态 | 已取消内容仍显示 | Worker 状态和请求代次双重校验 |
| 上游 Responses JSON 结构变化 | TUI 无法提取正文 | 文本提取失败时展示完整合法 JSON |
| Enter 被输入组件消费 | 无法提交 | 注册 App 级高优先级 Binding |
| Key 或错误体泄露 | 安全事故 | 中立安全错误、状态栏布尔显示、脱敏测试 |
| 新依赖与全局环境冲突 | 安装或验证失败 | 固定版本并在干净 Python 3.11 环境验证 |

## 18. 回滚方案

本变更不修改数据、不引入持久化，也不需要迁移脚本。

若 TUI 实现无法通过门禁：

1. 删除 `app/tui/`、`app/runtime/` 及对应测试。
2. 恢复 Router 直接调用 Service 的现有实现。
3. 恢复 Service 直接映射 FastAPI `HTTPException`。
4. 从 `requirements.txt` 移除 Textual 和 python-dotenv。
5. 回退 README、Knowledge 和索引更新。
6. 再次运行现有 HTTP 全量测试，确认原契约恢复。

回滚不涉及 `.env`、外部 API 配置或远程数据。
