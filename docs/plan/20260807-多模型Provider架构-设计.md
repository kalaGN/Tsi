# 多模型 Provider 架构设计

状态：已完成（2026-08-07）

对应需求：[多模型 Provider 架构需求](../spec/20260807-多模型Provider架构-需求.md)

## 1. 设计目标

把阿里云与 DeepSeek 的协议差异封装在 Provider 适配层，让 HTTP Router、TUI 和 Chat Runtime 只处理稳定的单轮文本结果。默认使用 DeepSeek，同时把 `/chat` 成功响应收敛为统一的 `{"output_text": "..."}`。

设计遵循轻量原则：使用现有 Python、HTTPX、FastAPI、Pydantic 和 Textual，不增加 SDK、依赖注入框架或运行基础设施。

## 2. 当前结构与问题

当前依赖为：

```text
HTTP Router ──┐
              ├──> Chat Runtime ──> Aliyun Responses Service
Textual TUI ──┘                           │
     └────────── 自行解析阿里云响应 <─────┘
```

存在四个具体耦合点：

1. Runtime 直接导入阿里云函数和阿里云异常。
2. `CHAT_PROVIDER`、`CHAT_MODEL` 在 Runtime 中硬编码。
3. TUI 直接读取 `DASHSCOPE_API_KEY`，并自行理解阿里云响应结构。
4. Router 原样输出上游 JSON，公开响应随 Provider 协议变化。

## 4. 核心契约

### 4.1 Provider 协议

`contracts.py` 定义结构类型，不读取环境变量、不发起网络请求：

```python
from dataclasses import dataclass
from typing import Any, Protocol


@dataclass(frozen=True)
class ProviderResult:
    """保存协议原始结果，并向上层提供稳定文本。"""

    upstream_status: int
    raw_body: Any
    output_text: str


class LlmProvider(Protocol):
    name: str
    model: str
    api_key_configured: bool

    async def generate(self, input_text: str) -> ProviderResult:
        ...
```

- `name` 使用稳定小写标识 `aliyun`、`deepseek`，展示层需要时再转换标题格式。
- `model` 是解析默认值和环境变量覆盖后的实际模型。
- `api_key_configured` 只表示非空密钥是否存在，不暴露密钥。
- `raw_body` 仅供适配器级测试和后续内部诊断扩展；Router 与 TUI 不读取它。

### 4.2 共享 Provider 异常

`contracts.py` 统一定义：

```text
LlmProviderError
├── ProviderConfigurationError
├── ProviderTimeoutError
├── ProviderConnectionError
├── ProviderAuthenticationError
├── ProviderResponseError
└── ProviderInvalidResponseError
```

异常只携带安全的 `user_message` 和可选 `status_code`。不得携带响应正文、Header 或密钥。Runtime 使用 `isinstance` 分类，避免依赖具体 Provider 的异常类。

配置错误细分为两个安全文案：

- 非法 `LLM_PROVIDER`：`Unsupported LLM provider configuration`。
- 缺少所选 Provider 密钥：`Upstream API key is not configured`。

其他现有用户文案保持不变。

### 4.3 Runtime 结果与状态信息

Runtime 暴露：

```python
@dataclass(frozen=True)
class ChatResult:
    output_text: str
    provider: str
    model: str


@dataclass(frozen=True)
class ChatRuntimeInfo:
    provider: str
    model: str
    api_key_configured: bool
```

- `run_chat(input_text, provider=None)` 默认通过工厂创建 Provider；测试可以注入 Fake Provider。
- `get_chat_runtime_info()` 通过同一个工厂解析配置，供 TUI 初始化状态栏。
- `ChatResult` 不携带原始 JSON 或上游成功状态码，避免界面重新绑定上游协议。

## 5. 配置设计

### 5.1 解析规则

`factory.create_provider(environ=None)` 接收可选只读环境映射，默认读取 `os.environ`：

1. `LLM_PROVIDER` 不存在时选择 `deepseek`。
2. 显式空白值或不支持的值抛出配置错误。
3. Provider 值去除首尾空白并转为小写后匹配。
4. 对应模型变量不存在或为空白时使用默认模型。
5. 密钥去除首尾空白后判断是否配置；真实值只保存在 Provider 实例内部。

配置矩阵：

| Provider | URL | Key | Model env | Default |
| --- | --- | --- | --- | --- |
| `aliyun`（显式选择） | 现有阿里云 Responses URL | `DASHSCOPE_API_KEY` | `ALIYUN_MODEL` | `qwen3-max` |
| `deepseek`（默认） | `https://api.deepseek.com/chat/completions` | `DEEPSEEK_API_KEY` | `DEEPSEEK_MODEL` | `deepseek-v4-flash` |

上游 URL 不开放环境覆盖，以限制误配和任意外连风险。测试通过 MockTransport 截获固定 URL，不依赖改写 URL。

### 5.2 生命周期

每次 `run_chat` 创建轻量 Provider，每次 Provider 调用创建并关闭一个 `httpx.AsyncClient`，保持现有资源生命周期。当前没有吞吐和连接复用需求，不引入应用级 Client 生命周期管理。

## 6. 网络边界

### 6.1 共享 HTTP 调用

`http_client.post_json(url, api_key, payload)` 负责：

- 使用 `Authorization: Bearer ...`、`Content-Type: application/json`、`Accept: application/json`。
- 使用现有 `httpx.Timeout(60.0, connect=10.0)`。
- 将 HTTPX Timeout、RequestError 转换为共享异常。
- 将 401/403 转换为鉴权错误。
- 将其他非成功状态转换为携带状态码的通用上游错误。
- 成功响应必须能解析为 JSON，否则抛出无效响应错误。
- 永不把上游错误正文放入异常或输出。

密钥存在性由 Provider 在调用共享 HTTP 函数前检查，确保缺少密钥时不会构造网络请求。

### 6.2 阿里云适配器

请求：

```json
{
  "model": "qwen3-max",
  "input": "用户输入"
}
```

文本提取按以下顺序执行：

1. 非空字符串 `body.output_text`。
2. `body.output[*].text` 中的非空字符串，按顺序用换行连接。
3. `body.output[*].content[*].text` 中的非空字符串，按顺序用换行连接。
4. 无法提取时抛出 `ProviderInvalidResponseError`，不再把整个 JSON 交给 TUI 展示。

这覆盖当前 TUI 已支持的阿里云响应形态，并把协议知识迁移到适配器。

### 6.3 DeepSeek 适配器

请求：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "user", "content": "用户输入"}
  ],
  "stream": false
}
```

文本提取路径固定为 `body.choices[0].message.content`。`body`、`choices`、首个 choice、`message` 或 `content` 类型不符合预期时，抛出 `ProviderInvalidResponseError`。

本期不发送 `thinking` 参数，使用所选 DeepSeek 模型的服务端默认行为；响应中的 reasoning、usage 和其他字段保留在内部 `raw_body`，不进入统一 HTTP 响应。

## 7. 用例与接口设计

### 7.1 Runtime 流程

```text
run_chat(input)
  -> 校验严格非空文本
  -> 使用注入 Provider，或从 factory 创建当前 Provider
  -> await provider.generate(input)
  -> ProviderError 映射为 ChatRuntimeError
  -> 返回 ChatResult(output_text, provider, model)
```

输入校验继续在 Router 和 Runtime 两层存在：Router 保护 HTTP 边界，Runtime 保护 TUI 和其他直接调用方。

### 7.2 HTTP 契约

请求保持：

```json
{
  "input": "你是谁？"
}
```

新增显式 Pydantic 响应模型：

```python
class ChatResponse(BaseModel):
    output_text: str
```

成功固定为：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"output_text": "模型生成的文本"}
```

Router 不接收或返回 Provider、模型、原始响应、Token usage。原有错误状态映射保持：

| Runtime 错误 | HTTP 状态 |
| --- | --- |
| 输入非法 | 422 |
| 配置错误 | 503 |
| 超时 | 504 |
| 连接错误 | 502 |
| 无效成功响应 | 502 |
| 鉴权错误 | 保留上游 401/403 |
| 其他上游错误 | 保留上游状态码 |

### 7.3 TUI

- 删除 `format_response_body()` 及其 JSON fallback。
- 成功时直接显示 `result.output_text`。
- 构造函数从 `get_chat_runtime_info()` 获得 Provider、模型和 Key 状态；测试可注入 `ChatRuntimeInfo`。
- 状态栏显示例如 `Deepseek | deepseek-v4-flash | Key: configured | Ready`。
- 配置非法时 TUI 启动为 Error 状态，并显示安全配置错误；不能因为读取状态信息而崩溃。
- 输入、取消、双击 Esc、耗时和命令行为不变。

## 10. 安全、可靠性与性能

### 安全

- Provider URL 固定，避免通过环境变量改变网络目标。
- API Key 只用于 Authorization Header，不进入 dataclass repr、Runtime 结果、HTTP/TUI 输出或测试快照。
- Provider/Runtime 错误使用固定安全文案；上游错误体永不透传。

### 可靠性

- 保持连接 10 秒、总计 60 秒超时。
- 不重试非幂等生成请求，避免重复计费和请求放大。
- 每次请求独立关闭 HTTP Client，不新增全局可变资源。
- 未知或空白 Provider 立即失败，不静默回退到阿里云。

### 性能

- 新增工厂和 dataclass 的成本相对模型网络耗时可忽略。
- 继续每次创建 HTTP Client，未优化连接复用；当前没有性能基线，暂不引入生命周期复杂度。
- 原始响应只在当前调用栈中存在，不做持久化或额外复制。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| `/chat` 响应改为统一结构 | 旧调用方读取原始字段失败 | README 明确迁移；测试锁定 `output_text`；不提供隐式双结构 |
| 阿里云响应形态不完整 | 合法响应被判为无效 | 迁移当前已支持的三种提取路径并为每种写测试 |
| DeepSeek 模型名称更新 | 默认模型未来失效 | 默认值集中在适配器；允许 `DEEPSEEK_MODEL` 覆盖；文档记录官方来源 |
| TUI 状态与实际调用配置不一致 | 用户误判 Provider | 状态与调用共用同一工厂解析规则，不直接读取环境变量 |
| 共享 HTTP 层过度抽象 | Provider 特性难扩展 | 仅共享认证、请求、错误和 JSON 解析；Payload 与文本提取留在适配器 |
| 密钥或错误正文泄漏 | 安全风险 | 固定错误文案、Mock 泄漏断言、禁止输出 raw body |

## 12. 回滚方案

本次不涉及数据库、持久化或远程资源变更。若需要回滚：

1. 恢复 Runtime 对旧阿里云 Service 的调用。
2. 恢复 Router 原始 JSON 响应和 TUI 旧提取逻辑。
3. 恢复旧测试并删除 `app/services/llm/`。
4. `LLM_PROVIDER`、`ALIYUN_MODEL`、`DEEPSEEK_*` 即使仍存在也不会被旧代码读取。

回滚后依赖旧原始响应的客户端恢复；已迁移到统一 `output_text` 的客户端将不再兼容，因此发布时必须把接口迁移与代码变更视为同一个发布单元。

## 13. 设计确认项

进入任务拆解前确认以下设计：

1. 使用 `app/services/llm/` 包，不引入额外架构层或第三方 SDK。
2. Provider 结果内部保留原始 JSON，Runtime/HTTP/TUI 仅接触统一文本。
3. `/chat` 固定返回 `200` 和 `{"output_text": "..."}`。
4. TUI 状态通过 Runtime 信息接口获取，不直接读取 Provider 环境变量。
5. 共享 HTTP 层负责通用安全错误，具体适配器负责 Payload 和文本提取。
6. 阿里云提取失败和 DeepSeek 响应结构异常统一视为 502 无效响应。
