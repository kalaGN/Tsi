# 当前对话上下文设计

状态：已完成（2026-08-08）

对应[需求](../spec/20260807-当前对话上下文-需求.md)和[任务](../tasks/20260807-当前对话上下文-任务.md)。

## 1. 设计摘要

- `services.llm` 定义 `ChatMessage` 和有序消息 Provider 契约，两个 Adapter 只负责协议映射。
- `runtime.chat` 保留无状态 `run_chat()` 给 HTTP，增加内部多轮调用能力。
- `runtime.session` 持有已提交消息，串行化发送，仅在 Provider 和 Store 均成功后提交新轮次。
- `runtime.session_store` 负责版本化 JSON、校验、原子写入和清理。
- TUI 默认加载唯一 Session，恢复界面；HTTP 不持有 Session。

## 2. 依赖方向

```text
HTTP -> runtime.chat -> Provider
TUI  -> runtime.session -> runtime.chat -> Provider
                    \-> runtime.session_store -> data/chat-session.json
```

Store 使用标准库，不依赖 Textual、FastAPI 或 Provider。TUI 不自行拼接历史。

## 3. 数据格式

```json
{
  "version": 1,
  "messages": [
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好！"}
  ]
}
```

恢复时只接受从 `user` 开始、`user/assistant` 严格交替且以 `assistant` 结束的完整轮次。未知字段不影响当前版本，未知版本拒绝加载。

## 4. 一致性与错误

1. Session 在 `asyncio.Lock` 内构造候选历史并调用 Provider。
2. Provider 成功后，Store 先写同目录临时文件，刷新后用 `os.replace` 替换目标。
3. Store 成功后 Session 才替换内存消息。
4. Provider 错误、取消或 Store 错误均不提交新轮次。
5. 损坏文件不自动覆盖；TUI 显示中立错误并阻止发送，`/clear` 成功后恢复。

## 5. 兼容与安全

- HTTP `/chat` 继续将单个输入包装为一条 user 消息，公开契约不变。
- 阿里云单轮仍发送 `input: string`；多轮才发送消息数组。
- 会话文件和日志都可包含明文对话，两个目录都不进入 Git。
- 持久化失败不暴露本地路径或底层异常。

## 6. 回滚

删除 Session/Store 模块并让 TUI 重新调用 `run_chat` 即可恢复无状态行为；Provider 的消息契约需同步回退。`data/chat-session.json` 是运行时数据，不参与代码回滚。
