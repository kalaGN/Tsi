# 模型输入输出日志设计

状态：已完成（2026-08-07）

对应需求：[`docs/spec/20260807-模型调用日志-需求.md`](../spec/20260807-模型调用日志-需求.md)

## 1. 方案

保持现有启动配置、Handler 和转储机制，扩展日志契约为两类事件：

```text
HTTP/TUI
   -> Chat Runtime
      -> llm_request(request_id, provider, model, input_chars, input_text)
      -> Provider.generate(input_text)
      -> llm_response(request_id, provider, model, output_chars, output_text)
      -> ChatResult
```

Provider 抛出异常时流程在 `llm_request` 后终止，不写 `llm_response`。

## 2. 日志模块

`app/observability/model_logging.py` 保留现有 `configure_model_logging()` 和 `new_request_id()`，调整为事件感知 Formatter：

- `llm_request` 白名单：`request_id`、`provider`、`model`、`input_chars`、`input_text`。
- `llm_response` 白名单：`request_id`、`provider`、`model`、`output_chars`、`output_text`。
- 通用字段：`timestamp`、`level`、`event`。

接口：

```python
def log_model_request(
    *, request_id: str, provider: str, model: str,
    input_chars: int, input_text: str,
) -> None: ...

def log_model_response(
    *, request_id: str, provider: str, model: str,
    output_chars: int, output_text: str,
) -> None: ...
```

两个精确接口不接收 API Key、Header、原始响应、任意字典或异常对象。Formatter 根据固定 `event` 选择白名单，不序列化 `LogRecord` 的其他属性。

## 3. Runtime

`run_chat()` 签名不变。在 Provider 创建成功后：

1. 生成一个 request ID。
2. 将同一 Provider/model 局部值用于请求与响应日志。
3. 在 Provider 调用前记录完整 `input_text`。
4. 只在 `generate()` 正常返回后记录完整 `result.output_text`。
5. 保持现有 Provider 错误转换不变。

不记录 `ProviderResult.raw_body` 或 `upstream_status`。

## 4. 序列化与文件

- 使用 `json.dumps(..., ensure_ascii=False, separators=(",", ":"))`，保留中文并将换行编码为 JSON 转义，每个事件仍是物理单行。
- stderr 和 `logs/model-calls.log` 使用同一 Formatter，两边内容一致。
- 保留 UTF-8、10 MiB、5 备份和写入失败降级。
- 完整正文可能使单条记录超过转储阈值；不为了保持文件上限而静默截断用户要求的内容。

## 5. 测试

- 请求与响应 JSON 字段集合精确，request ID 一致。
- 中文、引号、反斜杠和换行可从 JSON 无损还原，物理日志仍为单行。
- 成功 Runtime 调用顺序为 request log → Provider → response log。
- Provider 失败只写 request；空输入和配置失败仍不记录。
- 用假环境 API Key、假原始响应和假异常正文验证这些非业务内容不进入日志。
- HTTP JSON/Header、Provider 签名和 TUI 交互全量回归。

## 6. 风险与回滚

| 风险 | 缓解/已确认取舍 |
| --- | --- |
| 提示词或回答含隐私 | 明确写入 README 和 Spec；`logs/` 不入 Git；本期按用户要求不脱敏 |
| 输出到 stderr 被外部采集 | 文档显式说明双写边界；本期不对两个 Handler 设置不同内容 |
| 超大正文使文件超过 10 MiB | 不截断完整内容；保留 5 个历史备份，文档说明阈值不是严格磁盘配额 |
| 失败请求没有响应事件 | 不伪造输出；本期仍不引入失败事件 |

回滚时移除 `input_text` 和 `llm_response` 日志，恢复仅记录输入字符数的上一版实现。回滚不自动删除已经持久化的历史日志。

## 8. 已确认设计

1. 请求和成功响应分别记录为 `llm_request` 和 `llm_response`。
2. 两类事件包含完整明文，同时输出到 stderr 和本地文件。
3. 不截断、不脱敏、不增加开关，并接受单条超大日志可超过转储阈值。
