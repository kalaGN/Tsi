# Skill 安装与刷新设计

状态：已完成（2026-09-04）
创建日期：2026-09-04
对应需求：[Skill 安装与刷新需求](../spec/20260903-Skill安装与刷新-需求.md)

## 1. 设计结论

本次不把 Skill Catalog 改成随磁盘实时变化的可变对象，而是在 TUI 中增加一个进程级
`SkillRuntime`。它持有当前已发布的不可变 Catalog，并在每次用户发送消息时生成一份固定的
`ChatExecutionSnapshot`：

- system prompt 由启动时读取的 `AGENTS.md` 与当前 Catalog 摘要组合；
- Registry 由共享 Workspace Policy、共享撤销 Journal、当前 Catalog 和唯一 `install_skill` 工具组装；
- 当前 Provider Turn 从开始到结束只使用这一份快照；
- 安装成功后只发布下一版本，下一次用户请求才读取新快照。

`install_skill` 是 TUI 专属、必须逐次审批的变更工具。它从公开 GitHub Skill 目录或当前用户
`~/.codex/skills` 直属目录获取候选文件，在项目内隔离目录完成安全复制和现有 Catalog 校验后，
原子提交到 `.agents/skills/<expected_name>`。如果全量 Catalog 重建或发布失败，则删除本次目标并
继续使用旧版本。

HTTP `/chat` 继续使用默认 Registry，不感知 `SkillRuntime`、Home 目录或安装逻辑。

## 2. 当前代码事实

当前实现具有以下边界：

1. `app/tui/__main__.py` 启动时只加载一次 `AGENTS.md`、项目 Skill Catalog 和 Workspace Registry。
2. `ChatSession` 在构造时固定保存 `system_prompt` 与 `registry`，后续 `send()` 不重新读取。
3. `create_workspace_registry()` 每次创建一组 Workspace 工具；若 Catalog 非空，再追加
   `load_skill`、`read_skill_resource` 和 `run_skill_script`。
4. Skill 工具持有不可变 `SkillCatalog` 快照，脚本执行前还会核对磁盘内容哈希。
5. Workspace 写操作共享 `WorkspaceChangeJournal` 才能保持撤销链；热刷新不能为每次请求重置它。
6. 所有变更或执行类工具由 `ToolRegistry` 统一要求审批，TUI 使用 `ToolApprovalScreen` 展示预览。
7. `run_tool_loop()` 的审批日志当前按文件 Diff 形状读取字段，新增安装审批时必须按审批类型安全取值。
8. TUI 状态栏中的 Skill 数量是启动参数，当前没有运行时更新入口。

因此，仅在安装工具中重新调用 `load_skill_catalog()` 不足以实现热刷新；它既不能替换
`ChatSession` 已固定的 Registry，也可能让同一个 Provider Turn 同时使用新旧版本。

## 3. 目标架构

```text
TUI 启动
  -> 读取 AGENTS.md
  -> 创建 WorkspacePolicy + WorkspaceChangeJournal
  -> 创建 SkillRuntime(初始 Catalog)
       -> 创建持久 SkillInstaller / InstallSkillTool

每次 ChatSession.send
  -> SkillRuntime.snapshot()
       -> 当前 Catalog + 版本
       -> compose_system_prompt(AGENTS, Catalog.prompt)
       -> create_workspace_registry(..., Catalog, InstallSkillTool)
  -> 本轮固定使用 ChatExecutionSnapshot

install_skill 获批并成功
  -> 候选包进入项目临时目录
  -> 候选校验
  -> 原子提交目标目录
  -> 全量 load_skill_catalog()
  -> SkillRuntime.publish(new_catalog)
  -> 当前轮只返回“下一次请求生效”
  -> 下一次 send 获取新版本快照
```

依赖方向：

```text
app/tui -> app/runtime -> tools
tools/skill_installation -> tools/skills + tools/contracts
tools -X-> app/tui / Provider / HTTP Router
HTTP -> create_default_registry（保持不变）
```

## 4. 核心对象与职责

### 4.1 `ChatExecutionSnapshot`

在 `app/runtime/session.py` 增加不可变执行快照：

```python
@dataclass(frozen=True)
class ChatExecutionSnapshot:
    system_prompt: str | None
    registry: ToolRegistry | None
    version: int = 0
```

`ChatSession` 新增可选 `execution_snapshot_provider`。`send()` 获得会话发送锁后、构造本轮 Provider
请求前调用一次 provider，并把返回值保存为局部变量。旧的 `system_prompt`、`registry` 构造参数
继续保留为静态兼容路径，HTTP 和现有单元测试无需迁移。

约束：

- 一个 `send()` 最多取一次快照；工具循环中不再读取 Runtime。
- provider 异常转换为安全的配置错误，不提交会话历史。
- 快照不持久化到 Session 文件；Session 仍只保存 user/assistant 最终消息。
- 版本用于测试和诊断，不进入模型上下文和日志正文。

### 4.2 `SkillRuntime`

在 `app/runtime/skill_runtime.py` 增加 TUI 运行时组合对象，负责：

- 保存启动目录、启动时 `AGENTS.md`、Workspace Policy、共享 Journal 和当前 Catalog；
- 持有唯一 `SkillInstaller` 与 `InstallSkillTool`；
- `snapshot()` 基于当前 Catalog 创建 system prompt 和 Registry；
- `publish()` 以一次引用替换发布完整新 Catalog，并递增版本；
- `status()` 返回版本、Skill 数量和安全错误状态，供 TUI 状态栏读取。

`SkillRuntime` 不监控文件系统。项目目录的手动变化不会修改当前 Catalog；只有 TUI 重启或一次成功
安装会调用 `publish()`。

### 4.3 `SkillInstaller`

在 `tools/skill_installation.py` 增加安装用例对象。它持有：

- 已解析的项目根和项目 Skill 根；
- 启动时解析的个人 Skill 根；
- 异步安装锁；
- 可注入 GitHub 获取器；
- 成功后的 Catalog 发布回调。

安装锁覆盖“再次检查目标 -> 获取 -> 校验 -> 提交 -> 全量刷新 -> 发布/回滚”全过程，保证同一进程
并发安装串行化。同名目标只允许第一个成功。

### 4.4 `InstallSkillTool`

工具定义固定为：

```json
{
  "name": "install_skill",
  "effect": "mutating",
  "parameters": {
    "source_type": "github | codex_home",
    "source": "受限来源",
    "expected_name": "合法 Skill 名称"
  }
}
```

`preview()` 只做纯参数解析、目标相对路径计算和审批指纹生成，不能访问网络、Home 或写磁盘。
`invoke()` 再次解析完全相同的参数，并校验刚批准的指纹后调用 `SkillInstaller`。批准状态逐次消费，
不能用于下一次安装，也不能传递给 `run_skill_script`。

成功结果：

```json
{
  "name": "using-superpowers",
  "path": ".agents/skills/using-superpowers",
  "source_type": "codex_home",
  "runtime_version": 2,
  "active_from": "next_request"
}
```

## 5. 来源适配

### 5.1 本机 Codex 来源

`source_type=codex_home` 时，`source` 只能是一个目录名，例如 `skill-using-superpowers`。不接受 `/`、
反斜杠、`.`、`..`、绝对路径或用户提供的 `~`。

实际来源固定为进程启动时解析的：

```text
<current-user-home>/.codex/skills/<source>
```

复制流程逐层使用 `lstat` 和无跟随读取，只接受普通目录与普通文件。符号链接、设备、Socket、FIFO、
目录层级或文件数量超限时整体失败。审批界面和工具结果只显示
`~/.codex/skills/<source>`，不显示 Home 绝对路径。

### 5.2 公开 GitHub 来源

第一版接受规范 URL：

```text
https://github.com/<owner>/<repo>/tree/<ref>/<skill-directory>
```

限制：

- scheme 必须是 `https`，Host 必须精确为 `github.com`，禁止 userinfo、端口、query 和 fragment；
- owner、repo、ref 和 Skill 子目录都必须存在；第一版 ref 是单个 URL path segment，含 `/` 的分支名
  不支持；
- 不接受仓库首页、`blob` URL、短链接、GitHub Enterprise 或任意下载 URL；
- 不读取 GitHub Token、SSH Agent、Git Credential Helper 或模型 API Key。

获取器通过固定 `https://api.github.com/repos/<owner>/<repo>/contents/...` Contents API 递归读取该目录，
每次请求显式传 `ref`，只接受 `file` 和 `dir` 类型。它不执行 Git、Hook、Skill 脚本或依赖安装。

边界建议固定为：总请求数不超过 70、文件不超过 65（含 `SKILL.md`）、候选正文总计不超过
1 MiB 加入口文件上限、单响应和累计网络正文另设 Base64 开销上限、连接/读取/总耗时显式限制。
HTTP 重定向默认关闭；请求目标始终由受信 API Host 在代码内构造，不使用响应中的
`download_url`。测试以假获取器完成，不访问真实 GitHub。

## 6. 候选校验与原子提交

安装只使用项目目录内、`.agents/skills` 外侧的随机临时目录，确保最终重命名位于同一文件系统。

```text
.agents/.skill-install-<random>/<expected_name>/...
```

流程：

1. 获得安装锁并再次确认 `.agents/skills/<expected_name>` 不存在。
2. 创建权限收紧的随机临时目录。
3. 来源适配器把受限普通文件写入 `<expected_name>`，不保留来源中的符号链接和特殊权限。
4. 在临时父目录上复用现有 `load_skill_catalog()`，验证 YAML 唯一键、UTF-8、metadata name、目录名、
   文件类型、数量、大小、Catalog prompt 和所有资源限制。
5. 再次确认目标不存在，使用同文件系统 rename 提交目标目录。
6. 对真实项目根全量执行 `load_skill_catalog()`；成功后发布新 Catalog。
7. 若第 6 步或发布失败，删除本次刚提交的目标，保留旧 Runtime；所有临时文件在 `finally` 清理。

安装工具不复用 Workspace 编辑 Journal，因为 Skill 安装不是模型可自由指定路径的文本编辑，且本期不提供
`undo_install_skill`。目标存在时永远拒绝，避免覆盖用户文件。

进程内安装锁保证本应用中的同名并发只有一个成功；最终提交前的存在性检查与 rename 冲突继续作为
外部进程竞争兜底。任何竞争失败都返回稳定冲突，不合并目录。

## 7. 审批、安全错误与日志

新增 `SkillInstallApprovalRequest`，字段仅包含：

- `source_type`；
- 安全展示用 `source_display`；
- 项目相对 `target_path`；
- `network_access`；
- 固定风险警告；
- 调用匹配字段与 SHA-256 指纹。

TUI Modal 对 GitHub 明示“将访问公开网络并写入项目”，对本机来源明示“将读取个人 Codex Skill 并
写入项目”；默认按钮仍为拒绝。Registry 对该审批类型做独立形状、长度、来源和指纹校验。安装审批
拒绝不做指纹去重，模型每次重试都必须重新获得批准。

新增稳定错误分类：

| 错误码 | 使用场景 |
| --- | --- |
| `skill_already_exists` | 目标已存在或同名提交竞争失败 |
| `skill_source_unavailable` | 合法来源不存在、GitHub 返回不可用状态或本地读取失败 |
| `skill_download_timeout` | GitHub 获取超时 |
| `skill_package_invalid` | 候选包结构、类型、名称或大小校验失败 |
| `skill_refresh_failed` | 提交后全量 Catalog 重建或发布失败且已回滚 |

模型只收到固定英文安全消息，不收到绝对路径、HTTP 响应正文或底层异常。已有工具日志继续记录模型传入
的完整参数和 ToolResult，因此 GitHub URL、个人目录名与安装结果会以明文进入 `logs/model-calls.log`；
文档必须明确这一点。

`run_tool_loop()` 按审批类型生成日志元数据：文件编辑保留 paths/diff 计数，脚本与安装使用零值或专属
非敏感计数，禁止直接假设所有请求都具有 `paths` 和 `diff_text`。

## 8. Registry 与 TUI 装配

`create_workspace_registry()` 增加可选 `install_skill_tool` 参数：

- TUI Runtime 始终传入，因此即使项目当前没有 Skill 或 Catalog 加载失败，模型仍能看到
  `install_skill`；
- Skill Catalog 非空时仍追加三个既有 Skill 工具，它们绑定本轮旧快照；
- Workspace Journal 从 Runtime 传入，每次创建 Registry 时不会丢失撤销历史；
- HTTP 不调用该安装装配路径。

`app/tui/__main__.py` 改为构造 `SkillRuntime`，并把它的 `snapshot` 交给 `ChatSession`。启动 Catalog
错误保留为状态栏错误；安装工具仍可用，但如果项目中已有损坏 Skill，全量刷新会失败并回滚新安装。

`ChatTuiApp` 在每轮请求结束后只读取 `SkillRuntime.status()`，更新 Skill 数量与错误状态，不重新扫描
文件系统。因此成功安装后状态栏立即显示新数量，但新 Skill 仍从下一次发送才进入 Provider 快照。

## 9. 兼容性与迁移

- `ChatSession` 的静态 system prompt/Registry 调用方式保持兼容；只有 TUI 主入口使用动态快照。
- HTTP `/chat`、Provider 请求协议、流式解析、Session JSON 格式和模型日志主结构不变。
- 已安装项目 Skill 目录格式不变，不迁移现有文件。
- `load_skill`、`read_skill_resource`、`run_skill_script` 的参数和结果保持不变。
- `install_skill` 不出现在默认 Registry，不改变 HTTP 工具预算。
- 无新增第三方依赖；GitHub 客户端复用项目现有 `httpx`。

## 10. 测试设计

### 10.1 安装单元测试

- 参数矩阵：合法/非法来源类型、额外字段、名称、目录名和 GitHub URL。
- 本地复制：合法包、来源缺失、符号链接、特殊文件、超限、名称不匹配、目标已存在。
- GitHub 获取：合法目录、404/限流、超时、响应类型错误、路径越界、文件/请求/正文超限。
- 审批：无回调、拒绝、批准、每次重新审批、参数在审批后变化。
- 原子性：验证失败无目标、提交竞争失败、刷新失败删除目标、临时目录始终清理。

### 10.2 Runtime 与 Session 测试

- 一次 `send()` 只调用一次 snapshot provider。
- 安装前启动的 Provider Turn 始终持有旧 Catalog、旧 prompt 和旧 Skill 工具。
- 安装成功后的下一次 `send()` 使用新版本并能 `load_skill`。
- 手动修改 `.agents/skills` 不会改变 Runtime。
- 发布失败保留旧版本与旧状态。
- 动态快照不进入 Session 持久化，恢复历史保持兼容。

### 10.3 TUI、HTTP 与回归测试

- 安装审批 Modal 展示安全来源、目标和正确风险文案，默认拒绝。
- 状态栏在成功后更新数量，失败后不虚增。
- TUI 空 Catalog 与错误 Catalog 时仍注册 `install_skill`。
- HTTP 默认工具列表不含 `install_skill`，HTTP 请求不访问 Home 或 GitHub。
- 现有 Skill 脚本审批、Workspace 撤销、流式输出、取消和 `/clear` 全部回归。

质量门禁：

```bash
.venv/bin/python -m compileall -q main.py app tools tests
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv/bin/python -m pytest -q
.venv/bin/python -m pip check
git diff --check
```

## 11. 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 当前轮使用新旧混合 Skill | `send()` 开始只取一次不可变执行快照 |
| 非法远端内容污染项目 | 项目内隔离获取、完整复用 Catalog 校验、最后原子提交 |
| 安装后全量 Catalog 失败 | 删除本次目标并保留旧 Runtime |
| GitHub URL 变成通用 SSRF | 只解析固定 github.com URL，实际请求 Host 在代码内构造 |
| Home 路径逃逸 | 来源只接受直属目录名，根路径启动时固定，无跟随复制 |
| 安装批准顺带执行脚本 | 安装与脚本使用不同审批对象和不同逐次指纹 |
| Registry 重建丢失撤销链 | Runtime 复用同一个 WorkspaceChangeJournal |
| 网络阻塞 TUI | 异步 HTTP、显式超时和取消传播 |
| 日志泄露来源信息 | 不记录响应正文/绝对 Home 路径，并在 README 明示参数日志边界 |

## 12. 回滚策略

代码层回滚可整体撤销本功能提交；现有 `.agents/skills` 格式和静态 Skill 读取不受影响。运行时安装的
Skill 是用户批准后创建的项目文件，不因代码回滚自动删除。

单次安装失败时：

1. 未 rename：删除随机临时目录，目标保持不存在；
2. 已 rename、刷新失败：只删除本次新建且身份匹配的目标，再清理临时目录；
3. Runtime 发布前失败：旧 Catalog 引用不变；
4. Runtime 发布成功：工具返回成功，不提供自动卸载或降级。

## 13. 已确认项

1. GitHub 第一版只接受 `https://github.com/<owner>/<repo>/tree/<ref>/<skill-directory>`，并通过
   匿名 GitHub Contents API 获取；含 `/` 的分支名第一版不支持。
2. `ChatSession` 在每次发送开始时读取一次动态执行快照，现有静态构造方式保留兼容。
3. 安装成功后状态栏可立即更新数量，但新 Skill 只从下一次用户发送开始进入模型上下文。
4. 安装不进入 Workspace 撤销 Journal，也不提供覆盖、升级、卸载或安装回滚命令。
