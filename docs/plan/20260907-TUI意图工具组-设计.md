# TUI 意图工具组设计

状态：已完成（2026-09-07）

创建日期：2026-09-07

对应需求：[TUI 意图工具组需求](../spec/20260907-TUI意图工具组-需求.md)

## 1. 设计目标

在不增加路由模型和关键词分类器的前提下，把 TUI 每轮首步从固定 13 个工具缩减为一个 `activate_tool_groups` 元工具。模型需要外部能力时先激活组，Tool Loop 在下一模型步骤前把新的工具定义同步给当前 Provider Turn。

设计保持以下不变量：

- 工具全集仍由宿主在请求边界构造和验证，模型只能选择组，不能定义工具。
- 工具组状态只存在于一次 `ChatSession.send` 创建的 Snapshot 中。
- 动态刷新只改变下一步发送的 Tool Schema，不重建 Turn、不丢失工具调用结果。
- 副作用工具的审批仍由原 `ToolRegistry` 强制执行。
- HTTP 继续使用普通 `ToolRegistry((GetCurrentTimeTool(),))`。

## 2. 总体架构

```text
SkillRuntime.snapshot(input)
    │
    ├─ 构造完整宿主工具 Catalog
    ├─ 构造 GroupedToolRegistry（初始仅激活元工具）
    └─ $skill 时预激活 skills
             │
             ▼
run_chat_messages -> Provider.create_turn(initial definitions)
             │
             ▼
run_tool_loop
    ├─ ModelStep: activate_tool_groups
    ├─ GroupedToolRegistry.execute -> 更新 active definitions
    ├─ Turn.replace_tools(active definitions)
    └─ 下一 ModelStep 只发送当前工具组
```

新增分层：

```text
ToolRuntime Protocol
├─ ToolRegistry                 固定工具集合，HTTP 与既有测试继续使用
└─ GroupedToolRegistry          请求级渐进式工具集合，仅 TUI 使用
```

## 3. 中立契约

### 3.1 ToolRuntime

在 `tools/contracts.py` 增加最小协议，供 Runtime 和 Session 依赖：

```python
class ToolRuntime(Protocol):
    @property
    def definitions(self) -> tuple[ToolDefinition, ...]: ...

    async def execute(
        self,
        call: ToolCall,
        context: ToolExecutionContext | None = None,
    ) -> ToolResult: ...
```

`ToolRegistry` 自然满足该协议，不改变现有构造和执行行为。`ChatExecutionSnapshot.registry`、`run_chat_messages` 和 `run_tool_loop` 改为依赖协议，而不是具体类。

### 3.2 LlmTurn 动态工具

`LlmTurn` 增加同步方法：

```python
def replace_tools(self, tools: tuple[ToolDefinition, ...]) -> None: ...
```

同步方法不执行 I/O，只替换下一次 `next()` 构造请求体时使用的不可变 tuple。阿里云和 DeepSeek Turn 都实现该方法；Provider 不理解组名。

Tool Loop 在每个模型步骤开始前记录定义快照。工具执行完成后，仅当 `registry.definitions` 发生变化时调用 `turn.replace_tools(...)`。静态 Registry 不触发刷新。

## 4. GroupedToolRegistry

新增 `tools/groups.py`，包含：

- `ToolGroup`：固定组名枚举。
- `ToolGroupDefinition`：组名、模型可见用途、工具名称 tuple。
- `ActivateToolGroupsTool`：模型可见元工具。
- `GroupedToolRegistry`：管理完整工具对象、组映射、当前激活组和激活次数。

### 4.1 构造验证

构造时一次性验证：

- 完整工具名称唯一，且全部通过原 `ToolRegistry` 定义校验。
- 每个组非空，工具名称均存在于完整 Catalog。
- 同名组唯一，组名只能来自固定枚举。
- `workspace_write` 展开后显式包含全部 `workspace_read` 名称。
- 初始预激活组必须属于当前可用组。

内部保留完整工具对象，但执行入口只委托给按当前可见工具重建的普通 `ToolRegistry`。因此模型伪造未激活工具名时，只会得到现有 `unknown_tool`，不能访问隐藏对象。

### 4.2 可见定义顺序

顺序稳定为：

1. `activate_tool_groups`
2. 按完整 Catalog 原始顺序筛选出的已激活工具

稳定顺序便于 Provider 请求测试、日志比较和缓存。重复激活不改变顺序。

### 4.3 激活状态

- 一次调用接受 `groups` 数组，最少 1、最多 5 项，元素由当前可用组 enum 限制。
- 重复名称、未知组和非法类型返回 `invalid_arguments`。
- 新增激活最多发生两次；只请求已激活组时返回 `changed: false`，不消耗追加次数。
- 第三次尝试扩大集合返回 `tool_group_limit`，原集合不变。
- 当前运行时不存在的组返回 `tool_group_unavailable`。
- 预激活属于请求初始化，不消耗追加次数。

成功结果示意：

```json
{
  "active_groups": ["workspace_read"],
  "available_tools": [
    "activate_tool_groups",
    "list_workspace_files",
    "search_workspace_text",
    "read_workspace_file",
    "get_workspace_git_status",
    "get_workspace_git_diff"
  ],
  "changed": true,
  "activations_remaining": 1
}
```

返回值继续由普通 Registry 包装为现有 `{ok,data}` 信封。

## 5. 工具组装配

保留 `create_workspace_registry(...)`，继续创建完整静态 Registry，避免改变既有 API 和工具测试。

新增 `create_intent_workspace_registry(...)`：

1. 使用共享私有函数构造与静态 Registry 完全相同的工具对象 Catalog。
2. 根据实际存在的工具建立可用组。
3. 构造 `GroupedToolRegistry`，可接受预激活组。

组映射：

```text
general
└─ get_current_time

workspace_read
├─ list_workspace_files
├─ search_workspace_text
├─ read_workspace_file
├─ get_workspace_git_status
└─ get_workspace_git_diff

workspace_write
├─ workspace_read 全部
├─ apply_workspace_edits
├─ run_project_check
└─ undo_workspace_change

skills
├─ load_skill
├─ read_skill_resource
└─ run_skill_script

skill_install
└─ install_skill
```

TUI `__main__` 给 `SkillRuntime` 注入新工厂；HTTP 和直接调用 `create_workspace_registry` 的代码不变。

## 6. SkillRuntime 请求快照

`SkillRuntime.snapshot(input_text)` 继续只解析一次 Catalog 引用：

- 没有显式 `$技能名`：构造无预激活组的 Registry。
- 有合法显式引用：构造后预激活 `skills`，同时保留当前显式 Skill Prompt。
- Catalog 为空时不提供 `skills` 组。
- 安装成功后仍只在下一次 Snapshot 使用新 Catalog；当前请求不能获得新 Skill 脚本执行能力。

`registry_factory` 契约显式增加可选 `preactivated_groups` 关键字；项目内测试工厂同步更新，不用运行时反射或 `hasattr` 猜测能力。

## 7. Provider 实现

### 7.1 阿里云 Responses

`AliyunTurn.replace_tools` 替换 `_tools`。下一次 `next()` 仍先追加上一轮 `function_call` 和 `function_call_output`，再用新工具 tuple 生成请求体。已有流式事件解析不变。

### 7.2 DeepSeek Chat Completions

`DeepSeekTurn.replace_tools` 替换 `_tools`。下一次 `next()` 仍追加 assistant tool calls 和 tool messages，再序列化新工具 tuple。已有流式参数拼接不变。

两个实现均只接受 tuple、拒绝非 `ToolDefinition` 元素，并拒绝在 Turn 已完成后刷新。

## 8. Tool Loop 顺序

每一步执行顺序：

```text
definitions_before = registry.definitions
step = await turn.next(previous_results)
记录 Token
校验工具预算
串行执行当前 step 的工具
definitions_after = registry.definitions
if definitions_after != definitions_before:
    turn.replace_tools(definitions_after)
进入下一步
```

激活调用与普通工具一样计入模型步骤、每步调用数、总工具调用数和现有工具日志。若模型伪造隐藏工具调用，当前可见 Registry 返回 `unknown_tool`。

## 9. 错误与安全

新增固定错误码：

| 错误码 | 条件 | 是否改变激活状态 |
|---|---|---|
| `invalid_arguments` | 参数类型、数量或重复名称非法 | 否 |
| `tool_group_unavailable` | 请求当前 Catalog 未提供的组 | 否 |
| `tool_group_limit` | 超过两次成功追加 | 否 |
| `unknown_tool` | 模型伪造未激活工具调用 | 否 |

安全不变量：

- 激活只扩大“可见并可请求”的宿主白名单，不执行组内工具。
- `ToolEffect.MUTATING/EXECUTING` 继续由内部普通 Registry 强制审批。
- 组映射不能来自环境变量、AGENTS.md、Skill Frontmatter 或模型输出。
- 激活失败原子化，不发布半组工具。
- 每轮新建 Grouped Registry，不共享可变集合。

## 10. 性能与 Token

- 普通请求：13 个工具降为 1 个工具，不增加模型步骤。
- 需要工具的请求：增加一次短激活步骤，后续只发送相关组。
- 只读代码分析：13 个工具降为 6 个。
- `$技能名` 首步：激活工具加 3 个 Skill 工具。
- 写代码任务：激活工具加 8 个 Workspace 工具。

不承诺固定 Token 节省比例；测试只验证请求体工具数量和集合。

## 11. 可观测性

不新增日志类型。现有日志记录 `activate_tool_groups` 调用、激活结果以及下一步 HTTP 请求中的真实工具数组。后续日志瘦身应保留 `tool_count`、`toolset_hash` 和激活结果元数据，不属于本次范围。

## 12. 兼容与回滚

- HTTP 默认 Registry 不变。
- `create_workspace_registry` 返回的完整定义不变。
- 工具名称、参数、结果、审批和路径策略不变。
- Session 历史不保存激活状态，旧历史无需迁移。
- 回滚时将 TUI 工厂切回 `create_workspace_registry`，即可恢复完整工具模式。
- 无数据库、文件格式、环境变量或依赖迁移。
