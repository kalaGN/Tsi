# TUI 应用职责收敛设计

状态：已完成（2026-09-09）

## 1. 设计依据

- 已确认需求：[TUI 应用职责收敛需求](../spec/20260909-TUI应用职责收敛-需求.md)。
- `ChatTuiApp` 当前约 1000 行、42 个方法，构造函数同时解析环境、恢复模型、创建 Session 并汇总启动错误。
- 请求 Worker、Timer、generation、流缓冲、审批和取消存在同一完整生命周期，但目前与键盘和 Palette 交互混合。
- 模型切换直接从 TUI 调用 LLM Factory 和 ModelSelectionStore，使界面层理解 Provider 创建与持久化失败。
- 现有 [TUI 职责拆分设计](20260905-TUI职责拆分-设计.md) 明确将请求生命周期保留在主应用；本设计是其后续阶段，以当前已增长的真实职责为依据更新该边界。

## 2. 总体方案

保持 TUI 目录扁平，只新增 `bootstrap.py`、`request.py` 和 Runtime `model_selection.py`。

```text
python -m app.tui
        |
        v
  tui.__main__
        |
        +--> Skill/Workspace 启动边界
        |
        v
  tui.bootstrap.build_tui_dependencies()
        |              |
        |              +--> runtime.model_selection
        |              +--> runtime.session
        |              +--> runtime.memory
        v
  TuiDependencies
        |
        v
  ChatTuiApp
        |
        +--> Palette / Transcript / StatusBar / InputHistory
        |
        +--> RequestCoordinator
                    |
                    +--> ChatRunner / ChatSession.send
                    +--> Textual Worker / Timer
                    +--> ToolApprovalScreen
```

依赖方向为：

```text
tui.__main__ -> tui.bootstrap -> runtime -> services.llm
                    |
                    +-> tools contracts/runtime

tui.application -> tui.request -> runtime/tools contracts
        |
        +-> tui widgets/state
```

Runtime 不导入 Textual 或任何 TUI 模块；`request.py` 不在运行时导入 `application.py`。

## 3. 启动装配

### 3.1 数据结构

`app/tui/state.py` 在已有 `RunStatus` 之外增加：

```python
@dataclass(frozen=True)
class StartupIssue:
    code: str
    message: str
    severity: IssueSeverity
    blocks_prompt: bool


@dataclass(frozen=True)
class TuiHealthState:
    issues: tuple[StartupIssue, ...] = ()

    def first_blocking_issue(self) -> StartupIssue | None: ...
    def has_error_status(self) -> bool: ...
    def without_code(self, code: str) -> "TuiHealthState": ...
```

`severity` 控制挂载时是否把状态栏标记为 Error，`blocks_prompt` 独立控制是否拦截发送，以保留当前 Skill 目录错误“显示 Error 但不阻止基础对话”的语义。

`app/tui/bootstrap.py` 定义：

```python
@dataclass(frozen=True)
class TuiDependencies:
    chat_session: ChatSession | None
    chat_runner: ChatRunner
    runtime_info: ChatRuntimeInfo
    model_selection: ModelSelectionService | None
    skill_runtime: SkillRuntime | None
    health: TuiHealthState
    system_prompt_loaded: bool
    workspace_enabled: bool
    skills_count: int
    clock: Clock
```

`ChatRunner` 和 `Clock` 定义在 `request.py`；为避免循环导入，`bootstrap.py` 只引用该中立类型，`request.py` 不导入 bootstrap。

### 3.2 生产装配

`build_tui_dependencies()` 接收启动入参：系统提示词及错误、Workspace Registry 及错误、SkillRuntime 及状态、ModelSelectionStore 和可选时钟。它按固定顺序：

1. 构造 `ModelSelectionService` 并解析候选。
2. 尝试恢复已保存 Provider；失败转换为非阻断 warning。
3. 获取 RuntimeInfo；配置错误转换为阻断 issue 和安全占位快照。
4. 解析 MemoryPolicy；非法配置转换为阻断 issue，同时使用安全默认值完成对象构造。
5. 尝试 `ChatSession.load()`；损坏历史保留原文件，返回一个可执行 `/clear` 的空内存 Session 和阻断 issue。
6. 从 Session、SkillRuntime 和启动入参生成其余有限快照。

`app/tui/__main__.py` 仍是生产组合根：它先加载 `.env`、日志、AGENTS、Skill 和 Workspace，再调用 `build_tui_dependencies()`，最后创建 `ChatTuiApp(dependencies)`。

### 3.3 测试装配

`bootstrap.py` 提供无磁盘副作用的 `injected_tui_dependencies()`：

```python
def injected_tui_dependencies(
    *,
    chat_runner: ChatRunner | None = None,
    chat_session: ChatSession | None = None,
    runtime_info: ChatRuntimeInfo,
    clock: Clock = time.monotonic,
    ...
) -> TuiDependencies: ...
```

- 必须显式提供 Runner 或 Session，两者都缺失时拒绝。
- 传入 Session 且未传 Runner 时使用 `session.send`。
- 不解析环境、不创建 Store、不读取生产 `data/`。
- 现有 TUI 测试逐步改为 `ChatTuiApp(injected_tui_dependencies(...))`。

这一设计改变了 `ChatTuiApp` 的 Python 构造签名，但不改变用户启动命令或外部 HTTP 契约。该类不是项目公开 SDK API；测试工厂保留等价注入能力。

## 4. 模型选择用例

`app/runtime/model_selection.py` 定义：

```python
@dataclass(frozen=True)
class ModelRestoreResult:
    provider: LlmProvider | None
    warning: str | None


@dataclass(frozen=True)
class ModelSwitchResult:
    runtime_info: ChatRuntimeInfo
    warning: str | None


class ModelSelectionService:
    @property
    def options(self) -> tuple[ModelOption, ...]: ...

    def restore(self) -> ModelRestoreResult: ...

    def switch(
        self,
        session: ChatSession,
        selection: ModelOption,
    ) -> ModelSwitchResult: ...
```

### 4.1 恢复

- Store 未注入或无保存项时返回空 Provider，不警告。
- Store 错误、候选不存在、Key 不可用、Provider 创建失败时返回现有稳定警告，不修改文件。
- 成功时返回完整 Provider，bootstrap 使用同一实例构造 RuntimeInfo 并注入 Session，避免展示和真实请求分叉。

### 4.2 切换

- 先验证所选项属于启动候选快照，且 Key 可用。
- 创建 Provider 成功后调用 `session.replace_provider()`。
- 替换成功后再保存选择；保存失败返回 warning，不回滚当前 Provider。
- 预期的创建和替换失败统一转换为 `ModelSelectionError` 及稳定 `user_message`，TUI 只展示该文案。
- TUI 根据 `ModelSwitchResult.runtime_info` 更新状态栏，不接触 Provider 实例。

## 5. 请求生命周期

### 5.1 协调器边界

`app/tui/request.py` 定义 `ChatRunner`、`Clock` 和 `RequestCoordinator`。为避免额外文件，同文件定义一个仅用于类型检查的小型 `RequestHost` Protocol：

```python
class RequestHost(Protocol):
    run_status: RunStatus
    is_mounted: bool

    def run_worker(...): ...
    def set_interval(...): ...
    def query_one(...): ...
    def write_request_message(self, role: str, content: str) -> None: ...
    async def push_screen_wait(self, screen: ToolApprovalScreen) -> bool: ...
    def refresh_request_skill_status(self) -> None: ...
    def focus_request_prompt(self) -> None: ...
```

Protocol 不在运行时导入 `ChatTuiApp`，也不建立通用 Port/Adapter 目录。`ChatTuiApp` 通过若干公开协调方法满足该协议，Widget 实际查询仍由 TUI 层完成。

`RequestCoordinator` 提供：

```python
@property
def is_active(self) -> bool: ...

def start(self, input_text: str) -> None: ...
def cancel(self, *, show_message: bool) -> None: ...
def finish_stream(self) -> None: ...
```

App 使用 `is_active` 决定输入和 Palette 是否可用，使用 `start()` 取代自行创建 Worker，使用 `cancel()` 统一处理 `/quit` 和 Esc。

### 5.2 状态所有权

Coordinator 独占以下状态：

- `_active_worker`
- `_generation`
- `_activity_timer`
- `_activity_started_at`
- `_activity_generation`
- `_stream_generation`

App 继续拥有 `_last_escape_at`，因为它是全局输入/退出手势，不是模型请求状态。

### 5.3 时序

```text
App 验证输入
  -> RequestCoordinator.start(input)
  -> generation + 1
  -> 清空旧流输出
  -> host.run_worker(_run(...), exclusive=True)
  -> host.set_interval(100ms)
  -> runner(delta/reset/approval/result callbacks)
  -> generation 和 worker 取消校验
  -> success/error rendering
  -> refresh Skill status
  -> stop Timer + clear stream + clear worker + focus prompt
```

取消先递增 generation，再停 Timer/流输出并取消 Worker；因此即使底层协程吞掉取消，后续 Delta、审批或最终结果也无法通过 generation 校验。

## 6. `ChatTuiApp` 调整

构造签名收敛为：

```python
def __init__(self, dependencies: TuiDependencies) -> None: ...
```

构造时只：

1. 保存有限启动快照。
2. 根据 Session 已提交 user 消息初始化 InputHistory。
3. 创建 `RequestCoordinator(self, runner, clock, workspace_enabled)`。

主应用保留：

- Textual 布局和 reactive `run_status`。
- 挂载历史与启动 issue 展示。
- 状态栏有限快照投影。
- 键盘、Palette、命令和 InputHistory 优先级。
- `/clear`、`/memory`、`/skills` 等本地 UI 协调。
- `/model` 选中后调用 `ModelSelectionService.switch()` 并展示结果。
- Esc 清空输入、关闭 Palette 和双击退出手势。

`_can_start_prompt()` 从 `TuiHealthState.first_blocking_issue()` 取得稳定阻断原因。`/clear` 成功后移除历史损坏 issue，但不清理系统提示词、Workspace 或 Skill issue。模型切换成功后移除模型配置 issue，再由统一健康状态推导就绪/Error 展示。

## 7. 异常契约

| 边界 | 场景 | 结果 |
| --- | --- | --- |
| Bootstrap | Runtime 配置错误 | 阻断 issue + 安全 RuntimeInfo 占位 |
| Bootstrap | Memory Policy 非法 | 阻断 issue + 默认 Policy，保持 App 可挂载 |
| Bootstrap | Session 文件损坏 | 阻断 issue + 可执行 `/clear` 的空 Session，保留文件 |
| Model restore | Store/候选/Key/Provider 失效 | 非阻断稳定警告，回退环境默认 |
| Model switch | Key 缺失 | “目标模型的 API Key 未配置。” |
| Model switch | Provider/Session 失败 | 稳定切换失败文案，原模型不变 |
| Model switch | Store 保存失败 | 新模型保留，追加现有保存 warning |
| Request | ChatRuntimeError | 显示 `user_message`、已落盘变更和耗时 |
| Request | 未知异常 | 只显示 `Unexpected internal error`、变更和耗时 |
| Request | 取消/陈旧结果 | 不写最终消息或统计，清理临时状态 |

安全文案在迁移中保持原文，不把底层异常、Provider 响应、密钥、路径或堆栈带入 TUI。

## 8. 状态与数据兼容

- 不修改 `chat-session.json` 或 `model-selection.json` Schema。
- 不新增磁盘文件。
- `TuiDependencies`、`StartupIssue`、`TuiHealthState` 和模型选择结果只是进程内类型。
- 已恢复 Session 的历史展示顺序、InputHistory 初始值和系统消息不变。
- StatusBar 仍只接收 Provider、模型、Key 布尔值、提示词/Workspace/Skill 摘要和 RunStatus，不获得密钥或完整系统提示词。

## 9. 安全与性能

### 9.1 安全

- Workspace 工具审批流程仍由请求期回调连接 `ToolApprovalScreen`，默认拒绝。
- 取消代次校验和已落盘变更提醒必须作为整体迁移，不缩小保护范围。
- Bootstrap 不记录或返回密钥原文；模型恢复只处理安全标识和布尔状态。
- 测试不访问真实 Provider 或开发者真实数据文件。

### 9.2 性能

- 启动 I/O 次数不增加，只调整现有逻辑所在模块。
- 每个活动请求仍最多一个 100 ms Timer，空闲时无周期任务。
- 流式 Delta 仍在内存中累积并由 Timer 合并刷新，不为每个 Delta 重绘。
- 不增加模型请求、Token、工具步数或持久化操作。

## 10. 测试设计

### 10.1 Bootstrap

- 生产默认配置、有效保存模型、无效保存模型和 Key 缺失。
- MemoryPolicy 非法时返回可挂载依赖和阻断 issue。
- Session 恢复成功、损坏历史保留和 `/clear` 恢复路径。
- 注入 Runner/Session 的测试工厂不读取环境或生产 Store。

### 10.2 ModelSelectionService

- 候选快照不重读环境。
- 恢复的所有成功和降级分支。
- 切换时验证创建、Session 替换、Store 保存的顺序与失败语义。
- 返回 RuntimeInfo 与 Session 实际 Provider 一致。

### 10.3 RequestCoordinator

- 成功、Runtime 错误、未知错误和 finally 清理。
- Delta 合并、reset、工具审批状态变化和已落盘变更追踪。
- 取消后的迟到 Delta、审批和最终结果全部失效。
- 同时最多一个 Worker 和一个 Timer，空闲时两者都不存在。

### 10.4 集成回归

- 现有 `tests/test_tui.py` 的用户可见行为保持。
- 可将只验证内部私有字段的断言迁移到新单元测试；用户行为断言不删除。
- HTTP、Session、Memory、Tool、Skill、Provider 和日志全量回归通过。

## 11. 实施顺序与检查点

```text
TuiHealthState
      |
      v
ModelSelectionService
      |
      v
TuiDependencies + bootstrap
      |
      v
RequestCoordinator
      |
      v
ChatTuiApp 接入
      |
      v
测试去重 + 文档同步
```

1. 先建立健康状态与模型选择用例，用独立单元测试锁定契约。
2. 建立 bootstrap 和无副作用测试注入工厂，但暂不删除旧 App 路径。
3. 建立 RequestCoordinator 并在小型宿主测试中覆盖完整竞态。
4. 一次性将生产入口和 App 切到新依赖对象，再删除旧装配与请求实现，避免长期双路径。
5. 迁移测试、同步文档并执行全量门禁。

检查点：

- 模型选择用例完成后，其单元测试必须通过。
- Bootstrap 完成后，生产与注入路径测试必须通过。
- RequestCoordinator 接入后，全部 TUI 测试必须通过。
- 文档同步后执行 compileall、全量 pytest、pip check 和 diff check。

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 大量测试依赖旧 App 构造签名 | 迁移噪声大，难以判断真实回归 | 先增加统一测试工厂，机械替换构造点，保留行为断言 |
| Coordinator 与 App 双方都保留 Worker 状态 | 取消竞态和重复请求 | 所有权一次迁移，App 只查询 `is_active` |
| 抽取时改变收尾顺序 | 流文本残留、Timer 泄漏或焦点丢失 | 用现有测试锁定 finally 次序，新增单请求单 Timer 断言 |
| 健康状态统一时误改阻断语义 | 原本可对话的 Skill 错误变成阻断 | 分离 severity 和 `blocks_prompt`，为每种 issue 写明确测试 |
| 模型切换的替换/保存顺序变化 | 状态栏、Session 和磁盘不一致 | 用有序假对象验证先替换后保存，保存失败不回滚 |
| 演进成过度分层 | 小项目文件碎片化 | 固定只新增三个源文件，本轮不新增目录或通用框架 |

## 13. 回滚

- 本轮不修改持久化 Schema，回滚不需要数据迁移。
- 若生产装配失败，可同步回退 `__main__.py`、`application.py` 与 bootstrap 接入，恢复旧构造路径。
- 若请求协调器出现竞态，可整体回退 `request.py` 接入，不保留两套并行生命周期。
- 新增类型只存在内存，删除新模块后不会留下不可读数据。
