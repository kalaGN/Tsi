# Web 工作区写入设计

状态：已完成（2026-09-19）

对应需求：[Web 工作区写入需求](../spec/20260919-Web工作区写入-需求.md)

## 1. 现状

Web 与 TUI 共用 `ChatSession` 和工具循环，但 Web 的请求快照使用只读 Registry，且调用 `ChatSession.send()` 时没有传入审批回调。TUI 已具备完整的 `ToolApprovalRequest → Diff 展示 → bool 决策 → ToolRegistry 执行` 链路，可以复用协议和 Workspace 安全边界，不能复用 Textual 界面。

## 2. 架构

```text
Web 页面
  ├─ POST /ui/api/chat（NDJSON）
  │    └─ WebUiService.stream_message
  │         ├─ ChatSession.send(on_tool_approval=...)
  │         ├─ Web 写入专用 GroupedToolRegistry
  │         └─ WebApprovalCoordinator
  │              └─ tool_approval_required 事件 → 等待 Future
  └─ POST /ui/api/tool-approvals/{approval_id}
       └─ 校验 request_id + 一次性完成 Future
```

新增 `app/webui/approvals.py` 隔离请求级审批状态。协调器在单个进程内最多保存一个待审批对象；对象只包含随机审批 ID、当前请求 ID 和 asyncio Future，不持久化工具参数、Diff、Fingerprint 或批准状态。

## 3. 工具边界

在 `tools/workspace.py` 增加 Web 专用 Registry 工厂，固定包含：

- `general`：`get_current_time`
- `workspace_read`：现有五个 Workspace/Git 读取工具
- `workspace_write`：读取工具，加 `apply_workspace_edits`、`delete_workspace_file`、`run_project_check`、`undo_workspace_change`

该工厂不构造 Git 写工具、Skill 工具、安装工具或脚本工具。初始仍只向模型披露 `activate_tool_groups`，由模型在下一步骤按意图激活写工具组。

## 4. 审批协议

### 4.1 流事件

```json
{
  "type": "tool_approval_required",
  "request_id": "...",
  "sequence": 4,
  "session_id": "...",
  "approval_id": "服务端随机值",
  "tool": "apply_workspace_edits",
  "title": "应用工作区修改",
  "paths": ["app/example.py"],
  "diff": "--- a/app/example.py\n+++ b/app/example.py\n..."
}
```

只序列化 `ToolApprovalRequest` 的显示字段，不返回 Fingerprint。当前范围不会产生 Script、Skill 安装或 Git 审批；若未来错误传入其他审批类型，协调器失败关闭并让工具得到 `approval_unavailable`。

### 4.2 决策接口

```http
POST /ui/api/tool-approvals/{approval_id}
Content-Type: application/json

{"request_id":"...","approved":true}
```

- 成功：`{"accepted": true}`。
- 当前没有审批或 ID 不存在：404。
- 审批 ID 存在但请求 ID 不匹配：409。
- 非严格字符串/布尔值、空白或超长 ID：422。
- Future 完成后立即清除；重复提交返回 404。

## 5. 生命周期与并发

1. `stream_message` 创建 request ID、队列和 runner。
2. 写工具生成并由 Registry 验证审批预览。
3. 审批回调注册一次性 Future，先发送流事件，再等待页面决策。
4. 决策接口只完成完全匹配的 Future；工具循环恢复并记录原有审批日志。
5. 拒绝返回 `False`，由 Registry 生成 `approval_denied`，不执行工具。
6. 请求取消、流断开、失败或结束时取消 runner，并使该 request ID 的待审批状态失效。

现有全局 `_request_lock` 覆盖等待审批阶段，因此会话、模型和第二条消息继续被阻止。审批接口不获取该锁，否则会和等待它的请求死锁。

## 6. 页面交互

- 页面新增原生 `<dialog>`，纯文本 `<pre>` 展示 Diff，文件路径使用 `textContent`。
- 对话流收到审批事件后打开弹窗，默认焦点为“拒绝”。
- 批准/拒绝按钮在请求期间只提交一次；等待响应时禁用。
- Esc 等同拒绝。停止请求、终止事件或流断开时关闭弹窗并清空本地审批状态。
- 审批事件在活动面板显示“等待批准”，工具结束后显示现有成功/失败状态。
- 写工具成功后刷新文件树，使新增、删除文件可见。

## 7. 安全与异常

- 路由继续执行 loopback 校验。
- 客户端只回传不可预测审批 ID、请求 ID 和严格布尔决定，不能回传或覆盖 Diff、路径及参数。
- 工具参数、哈希、防符号链接、保护路径、文本与大小限制继续由现有 Workspace Tool 校验。
- 内部 Future、Fingerprint、绝对路径和异常文本不进入页面。
- 浏览器刷新会断开流并取消请求，不保留可恢复审批。

## 8. 测试与验证

- 为协调器写确定性异步单测，覆盖批准、拒绝、冲突、重复和取消清理。
- 使用脚本化 Provider 先请求 `workspace_write`，再请求编辑工具，证明批准前不落盘、批准后落盘及拒绝不落盘。
- Router 测试验证请求 ID 绑定、状态码和严格类型。
- 静态契约测试验证弹窗、事件名、API 路径和 `textContent`。
- 执行需求文档中的全部验证命令。

## 9. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 审批接口与流竞争 | Future 注册后再发送事件；一次性匹配并原子清除 |
| 断流遗留挂起请求 | 流生成器 `finally` 取消 runner 并失效审批 |
| 页面重复点击 | 前端立即禁用，后端 Future 只消费一次 |
| 意外开放 Git/脚本 | 使用独立 Web Registry 工厂和工具名断言测试 |
| Diff 注入 HTML | `<pre>.textContent`，不使用 `innerHTML` |

回滚时恢复 Web 只读 Registry，删除审批路由和页面弹窗即可；会话数据格式和已存在的正常文件无需迁移。
