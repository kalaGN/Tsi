# 任务预判与拆解：设计

对应需求：[任务预判与拆解需求](../spec/20260928-任务预判与拆解-需求.md)。

## 调用顺序

```text
用户输入 → 无工具预判（一次有界模型调用）
         ├─ direct  → 原有聊天或长任务执行
         ├─ planned → 展示最多 6 步 → 用户确认 → 原有执行
         └─ clarify → 展示问题，等待新输入
```

预判只接收当前输入和有界近期会话摘要，不触发 ChatSession 工具循环，不持久化一条假助手回答。输出使用固定 JSON 契约，严格检查分类、步骤数、文本长度及总输出长度。模型输出无效或超时即停止，不能默认按 `direct` 执行。执行时把已确认计划作为本轮有限上下文传入，但模型仍须检查实际工作区；计划不扩大工具权限。

## 生命周期与 UI

Web 在会话服务中保留一个带随机 ID、会话/项目/模型绑定的待确认计划；页面呈现“执行／取消”。TUI 使用同一预判结果并显示确认操作。待确认计划只存内存：重启后丢弃是安全的，因为计划阶段无副作用；原输入由用户重发即可。切换会话、项目或模型时失效，避免旧计划作用于新上下文。

显式长任务保持 `ready` 状态直到预判完成且用户确认；确认后才调用 `run_task_step()` 并增加尝试次数。普通聊天不写 `TaskRun`。`direct` 不等待确认但同样先完成一次预判。`clarify` 不把未执行的目标记作已完成对话。

## 成本和安全

- 新增一次模型往返不可避免；预判使用短输出预算、零工具定义与固定超时，页面应分别显示“判断中”和“执行中”。
- 预判只产生建议，不自动执行文件、脚本、Git 或外部 MCP。确认计划也不等于批准具体写操作。
- 结构化日志只记请求 ID、判断结果、耗时和步骤数；不新增输入正文或计划全文日志。
- 不修改现有长任务 JSON 记录格式；计划待确认态按进程内状态处理，以免引入不必要迁移。

## 风险与验证

- 用户输入存在指令注入：严格隔离 Planner 的系统指令与用户内容，无工具执行，格式校验失败关闭。
- 重复确认或跨会话确认：随机计划 ID 一次性消费，复验会话、项目、模型与忙碌状态。
- 预判后执行失败：沿用现有失败、取消和写操作人工检查语义，不自动重试。
- 性能：记录预判耗时和额外模型调用；不承诺比现有普通聊天更快。
