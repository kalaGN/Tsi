# 多模型 Provider 架构需求

状态：已完成（2026-08-07，包含 `/chat` 统一文本响应）

## 1. 背景

当前项目仅支持阿里云兼容模式 Responses API，并在 `app.runtime.chat` 中直接导入阿里云实现。HTTP 与 TUI 虽然共享 Runtime，但 Provider、模型、密钥检测和响应文本解析仍带有阿里云专属知识，增加 DeepSeek 时容易形成条件分支和重复错误处理。

本次需要重新划分大模型接入边界，在保留阿里云能力的同时支持 DeepSeek 官方 Chat Completions API，并让后续增加新 Provider 时不再修改 HTTP Router 或 TUI 的核心交互流程。

## 2. 已确认现状

- 真实依赖方向为 `HTTP/TUI -> Runtime -> Aliyun Service`。
- `POST /chat` 仅接收 `{"input": "非空字符串"}`，成功时原样返回所选上游的 JSON 和成功状态码。
- TUI 是非流式、无历史回传的单轮调用，当前自行从阿里云响应结构提取文本。
- 阿里云使用 `DASHSCOPE_API_KEY`、固定模型 `qwen3-max` 和固定 Responses API 地址。
- 网络调用使用现有异步 HTTPX；项目没有重试、连接池共享、工具调用或持久化。
- 自动化测试禁止请求真实付费接口。

## 3. 外部接口事实

根据 DeepSeek 官方文档：

- 基础地址为 `https://api.deepseek.com`，对话接口为 `POST /chat/completions`。
- 请求至少包含 `model` 和 `messages`；本项目单轮输入映射为 `messages: [{"role": "user", "content": input}]`。
- 非流式文本位于 `choices[0].message.content`。
- 当前模型标识为 `deepseek-v4-flash` 和 `deepseek-v4-pro`；旧的 `deepseek-chat`、`deepseek-reasoner` 已弃用，不作为默认值。
- 官方错误状态包含 400、401、402、422、429、500 和 503。

参考：

- [DeepSeek 创建对话补全](https://api-docs.deepseek.com/api/create-chat-completion)
- [DeepSeek 模型与价格](https://api-docs.deepseek.com/quick_start/pricing/?article_id=article_1779470751466_8)
- [DeepSeek 错误码](https://api-docs.deepseek.com/quick_start/error_codes/)
- [DeepSeek 更新记录](https://api-docs.deepseek.com/updates/)

## 4. 目标

1. 建立 Provider 无关的单轮模型调用边界。
2. 保留现有阿里云 `qwen3-max` 调用能力。
3. 新增 DeepSeek 官方 Chat Completions API 适配器。
4. 通过部署环境选择当前 Provider，不要求 HTTP/TUI 调用方理解上游协议。
5. Runtime 向 HTTP 与 TUI 提供同一份已规范化文本结果，隐藏 Provider 响应结构差异。
6. 对配置、网络、鉴权、上游状态和无效响应继续提供一致且脱敏的错误语义。
7. 新增 Provider 时，Router 和 TUI 不需要新增 Provider 专属解析逻辑。

## 5. 范围

### 5.1 Provider 选择

- 新增 `LLM_PROVIDER` 环境变量，可选值为 `aliyun`、`deepseek`。
- 未配置时默认 `deepseek`；使用阿里云必须显式设置 `LLM_PROVIDER=aliyun`。
- 非法或空白 Provider 配置应在调用前产生可诊断的配置错误，不发起网络请求。
- 本期不允许客户端在 `/chat` 请求体或 TUI 输入中动态指定 Provider。

### 5.2 模型与密钥配置

| Provider | 密钥变量 | 模型变量 | 默认模型 |
| --- | --- | --- | --- |
| Aliyun | `DASHSCOPE_API_KEY` | `ALIYUN_MODEL` | `qwen3-max` |
| DeepSeek | `DEEPSEEK_API_KEY` | `DEEPSEEK_MODEL` | `deepseek-v4-flash` |

- 密钥只从环境变量读取，不设置真实默认值，不输出到响应、日志或 TUI。
- 模型变量未设置或为空白时使用表中默认值。
- 上游 URL 由代码内受控 Provider 配置确定，本期不开放任意 URL 环境变量。
- TUI 状态栏显示当前 Provider、实际模型和密钥是否存在，但不显示密钥值。

### 5.3 Provider 抽象

Provider 边界至少提供以下能力：

- 标识 Provider 名称和实际模型。
- 判断所需密钥是否已配置。
- 接收一个非空单轮字符串并异步调用上游。
- 返回统一成功结果：上游状态码、原始 JSON、规范化文本、Provider 和模型；原始 JSON 仅保留在内部边界，不直接暴露给 HTTP 或 TUI。
- 抛出统一的配置、超时、连接、鉴权、上游响应和无效响应错误。

具体 Provider 负责自己的 URL、认证 Header、请求 JSON 和响应文本提取。Runtime 只依赖 Provider 契约，不导入某个具体上游的异常类型或响应结构。

### 5.4 阿里云适配

- 继续调用现有阿里云 Responses API。
- 请求保持 `{"model": 实际模型, "input": input_text}`。
- 保持现有连接超时 10 秒、总超时 60 秒及安全错误处理。
- 设置 `LLM_PROVIDER=aliyun` 时继续调用现有阿里云模型；`/chat` 请求和错误语义保持兼容，成功响应按本 Spec 统一为文本结构。

### 5.5 DeepSeek 适配

- 调用 `POST https://api.deepseek.com/chat/completions`。
- 使用 Bearer Token 和 JSON Content-Type。
- 非流式请求结构至少为：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {
      "role": "user",
      "content": "用户输入"
    }
  ],
  "stream": false
}
```

- 展示文本从 `choices[0].message.content` 提取；缺少该字符串时视为无效成功响应。
- 成功时在 Provider 结果内部保留 DeepSeek 原始 JSON，并向 Runtime 返回规范化文本。
- 401 归类为鉴权失败；其他非成功状态保留上游状态码并隐藏错误正文。
- 复用现有 HTTPX 和超时策略，不新增 SDK 依赖。

### 5.6 Runtime、HTTP 与 TUI

- Runtime 负责解析当前配置、获得 Provider、校验输入并转换统一错误。
- `POST /chat` 请求仍严格为 `{"input": "非空字符串"}`，不增加 `provider` 或 `model` 字段。
- HTTP 成功时不再透传上游 JSON，统一返回 `200 OK` 和稳定结构：

```json
{
  "output_text": "模型生成的文本"
}
```

- 阿里云与 DeepSeek 使用完全相同的 HTTP 成功响应结构；客户端不需要识别 Provider。
- 该调整是对现有 `/chat` 成功响应的显式破坏性变更：依赖阿里云原始响应字段的调用方必须改为读取 `output_text`。
- HTTP 错误继续使用 FastAPI `{"detail": "..."}`，现有输入校验和安全错误映射保持不变。
- TUI 直接展示统一结果中的文本，不再识别阿里云或 DeepSeek 的 JSON 结构。
- TUI 的 Enter、双击 Esc、`/clear`、`/quit`、中文输入和耗时统计保持不变。

## 6. 非功能要求

### 6.1 安全

- `.env` 继续被 Git 忽略；仓库文档和测试只能使用明显假密钥。
- 上游错误正文、Authorization Header、密钥和内部堆栈不得返回给 HTTP 客户端或显示在 TUI。
- 测试必须使用 HTTPX MockTransport，不访问真实阿里云或 DeepSeek。

### 6.2 可维护性

- Provider 专属协议只能存在于相应适配器中。
- 共享错误和结果类型只有一个权威定义，避免每个 Provider 重复声明同义异常。
- 工厂或注册表只承担配置到 Provider 的解析，不包含业务流程。
- Router 只把 Runtime 文本包装为 `{"output_text": result.output_text}`，不得解析 Provider 原始 JSON。
- 对协议转换、兼容原因和安全边界增加必要注释，不做逐行复述。

### 6.3 可靠性

- 本期保持现有超时，不新增自动重试；避免在没有幂等性和放大风险评估时改变行为。
- 配置错误必须在创建网络请求前暴露。
- Provider 返回 HTTP 成功但 JSON 不合法或缺少必需文本时，统一映射为无效响应。

## 7. 非目标

- 不实现流式响应、多轮上下文、系统提示词、工具调用、结构化输出或图片输入。
- 不支持单次请求动态切换 Provider 或模型。
- 不增加 OpenAI/DeepSeek SDK、依赖注入框架、数据库、缓存、队列或后台 Worker。
- 不实现自动降级、故障转移、负载均衡、重试、熔断或额度管理。
- 不改变 `GET /`、启动入口、TUI 键位和本地命令。
- 不把旧的 `deepseek-chat` 或 `deepseek-reasoner` 设为默认模型。

## 8. 兼容与迁移

- 默认 Provider 为 DeepSeek；现有仅配置 `DASHSCOPE_API_KEY` 的环境需要补充 `LLM_PROVIDER=aliyun` 才能继续使用阿里云。
- `/chat` 成功响应由阿里云原始 JSON 迁移为 `{"output_text": "..."}`；这是本次唯一计划中的公开 HTTP 破坏性变更。
- 调用方如果只需要生成文本，应改为读取顶层 `output_text`；本期不提供旧响应结构兼容开关。
- 使用 DeepSeek 时增加：

```dotenv
LLM_PROVIDER=deepseek
DEEPSEEK_API_KEY=replace-with-real-api-key
DEEPSEEK_MODEL=deepseek-v4-flash
```

- `ALIYUN_MODEL` 和 `DEEPSEEK_MODEL` 均为可选配置。
- README、架构 Knowledge、API 约定、术语和排障文档需在实现完成后同步。
- 回滚到旧实现时，只需恢复 Provider 相关代码与文档；不涉及数据迁移和远程资源删除。

## 9. 可测试验收标准

1. 未设置 `LLM_PROVIDER` 并配置 DeepSeek 假密钥时，Mock 捕获到官方 URL、Bearer Header、默认模型、单轮 `messages` 与 `stream: false`。
2. 设置 `LLM_PROVIDER=aliyun` 时，阿里云请求 URL、Header、默认模型、输入结构和现有错误映射保持通过。
3. 两个 Provider 的自定义模型变量均能覆盖默认模型，空白值回退默认模型。
4. 非法 Provider、缺失所选 Provider 密钥时返回配置错误，且没有网络调用。
5. DeepSeek 成功结果在内部保留原始 JSON，并正确提取 `choices[0].message.content` 给 Runtime。
6. DeepSeek 的超时、连接错误、401、429、500、503、非 JSON 成功和缺少文本均得到预期安全错误，假密钥及上游错误体不泄漏。
7. HTTP `/chat` 请求 Schema 不变；两个 Provider 成功时均返回 `200` 和唯一字段 `output_text`，响应中不出现 Provider 原始字段。
8. 现有 HTTP 输入校验和错误映射回归测试继续通过；原始成功响应测试替换为统一文本响应测试。
9. TUI 状态栏随配置显示正确 Provider/模型/密钥状态，且交互、中文输入、取消和耗时测试继续通过。
10. 不新增第三方依赖，真实验证命令全部通过：

## 10. 已确认决策

以下方案已确认并作为详细设计依据：

1. Provider 仅由 `LLM_PROVIDER` 做部署级选择，不向 `/chat` 增加选择字段。
2. 默认使用 DeepSeek；阿里云通过 `LLM_PROVIDER=aliyun` 显式选择。
3. DeepSeek 默认模型使用当前官方的 `deepseek-v4-flash`；需要更强模型时通过 `DEEPSEEK_MODEL=deepseek-v4-pro` 配置。
4. HTTP 与 TUI 都使用 Provider 统一提取出的文本；HTTP 固定返回 `{"output_text": "..."}`，不再透传上游 JSON。
5. 本期使用 HTTPX 直接接入，不引入额外 SDK。
