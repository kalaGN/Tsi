# 外部模型请求日志需求

状态：已完成（2026-08-08）

## 1. 背景与目标

当前 `logs/model-calls.log` 只记录 Runtime 视角的当前输入和统一输出，不能回答一次外部模型调用实际发到哪里、发了什么、用了什么超时配置，以及外部 HTTP 是否返回。

本次要让本地日志能回答：

1. 该 request ID 实际调用了哪个 Provider、模型、URL 和 HTTP 方法？
2. 实际发送的安全 Header、完整 JSON 请求体和超时配置是什么？
3. 外部 HTTP 返回了什么状态码、耗时多久，或在哪一类网络错误上失败？

## 2. 与现有 Spec 的关系

本需求明确变更[20260807-模型调用日志-需求.md](20260807-模型调用日志-需求.md)的以下历史决策：

- 原“不记录耗时、失败分类或上游状态码”改为记录 HTTP 层耗时、状态码和有限失败分类。
- 原“不修改 Provider 或共享 HTTP 客户端签名”不再适用；为传递 request ID、Provider 和模型上下文，允许修改内部契约。
- 原有 `llm_request` / `llm_response` 事件及字段保持兼容，不重命名或删除。

## 3. 结构化事件契约

所有事件继续写入 stderr 和 `logs/model-calls.log`，使用同一 32 位 request ID 关联。

### 3.1 `llm_http_request`

在 `httpx.AsyncClient.post()` 前记录：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` | string | 与 Runtime 事件一致 |
| `provider` | string | `aliyun` 或 `deepseek` |
| `model` | string | 实际模型 |
| `method` | string | 固定 `POST` |
| `url` | string | 实际上游 URL |
| `headers` | object | 仅允许 `Accept`、`Content-Type` 和脱敏 `Authorization` |
| `request_body` | object | 实际发送的完整 JSON，包含多轮历史 |
| `timeout` | object | `connect_seconds` 和 `total_seconds` |

`headers.Authorization` 固定写为 `Bearer [REDACTED]`，不接收、保存或格式化真实 API Key。

`request_body` 必须是实际交给 HTTPX `json=` 的完整对象，不用摘要、计数或当前输入代替。例如 DeepSeek 多轮请求日志中必须包含：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "user", "content": "第一问"},
    {"role": "assistant", "content": "第一答"},
    {"role": "user", "content": "第二问"}
  ],
  "stream": false
}
```

阿里云单轮保留实际的 `input: "..."`，多轮则记录实际的 `input: [{"role": ..., "content": ...}]` 数组。换言之，DeepSeek 的 `messages` 和阿里云的 `input` 都不得丢失、截断或脱敏对话文本。

### 3.2 `llm_http_response`

外部 HTTP 收到响应后、业务状态映射前记录：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` / `provider` / `model` | string | 关联上下文 |
| `status_code` | integer | 外部 HTTP 状态码，包含非 2xx |
| `duration_ms` | number | 从发起到收到响应的单调时钟耗时 |
| `response_content_type` | string/null | 仅记录 Content-Type |

不记录原始响应体、全部响应 Header 或 Cookie。成功统一文本仍由现有 `llm_response.output_text` 记录。

### 3.3 `llm_http_error`

连接失败或超时时记录：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `request_id` / `provider` / `model` | string | 关联上下文 |
| `error_type` | string | 只能为 `timeout` 或 `connection` |
| `duration_ms` | number | 失败前单调时钟耗时 |

不记录异常类名、异常原文、Traceback 或请求对象。HTTP 非 2xx 已收到响应，属于 `llm_http_response`，不重复写 `llm_http_error`。

## 4. 安全与隐私边界

- 采用事件字段白名单，禁止序列化 `httpx.Request`、`httpx.Response`、LogRecord 或异常对象。
- API Key、真实 `Authorization`、Cookie、代理凭据、上游原始响应和异常原文绝不进入日志。
- `request_body` 会以明文重复保存当前输入和全部多轮历史，日志量和隐私风险随会话长度增长。
- 不将日志接入远程采集，`logs/` 继续由 Git 忽略，现有 10 MiB 转储和 5 个备份不变。

## 5. 实现边界

- Runtime 生成 request ID，显式传给 Provider，Provider 再传给共享 HTTP 层；不使用全局变量或隐式 `ContextVar`。
- 共享 HTTP 层在真实 I/O 边界记录事件，Provider 不复制日志代码。
- 日志失败继续不影响模型请求。
- 使用 `time.monotonic()` 计算 HTTP 耗时，单位毫秒，保留两位小数。
- 不新增第三方依赖，不增加指标、Trace、告警或 HTTP request ID Header。

## 6. 测试策略

- Formatter 测试四类事件的精确字段白名单、单行 JSON 和 request ID 关联。
- HTTP MockTransport 测试 DeepSeek/阿里云的实际 URL、脱敏 Header、完整单轮/多轮请求体、状态码和耗时。
- 超时和连接失败测试只产生有限错误分类，异常原文和假 API Key 不出现。
- HTTP、TUI、Session、Provider 和日志转储全量回归，自动测试不访问真实外部服务。

项目门禁：

```bash
.venv/bin/python -m compileall -q main.py app tests
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv/bin/python -m pytest -q
.venv/bin/python -m pip check
git diff --check
```

## 7. 非目标

- 不记录上游原始响应体、所有响应 Header、Cookie、重定向链、TLS 详情或底层连接池信息。
- 不增加重试、指标、Trace、告警、日志远传、日志查询 UI 或新配置开关。
- 不改变 HTTP `/chat`、TUI、Session 或模型上下文行为。

## 8. 可测试验收标准

1. 成功模型调用按 `llm_request -> llm_http_request -> llm_http_response -> llm_response` 顺序产生四条可关联事件。
2. `llm_http_request` 反映实际 Provider URL、POST、脱敏 Header、完整 JSON 请求体和 10/60 秒超时；DeepSeek `messages` 或阿里云 `input` 必须与实际发送内容一致。
3. 外部非 2xx 产生 `llm_http_response`，包含真实状态码和可控耗时，不产生 `llm_response`。
4. 超时/连接失败产生 `llm_http_error`，仅包含安全类型和可控耗时。
5. 任何事件均不包含真实 API Key、完整 Authorization、原始响应体、异常原文或 Traceback。
6. 多轮 TUI 的 `request_body` 完整包含已提交历史与当前 user 消息，角色顺序与实际上游请求一致。
7. 日志文件、转储、HTTP 公开契约和现有功能回归全部通过。

## 9. 待确认决策

1. 记录完整外部 JSON 请求体，包括 DeepSeek `messages` 或阿里云 `input` 中所有 `role/content`；因此多轮历史会在每次调用时重复明文落盘。
2. Authorization 只记录 `Bearer [REDACTED]`，其他非白名单 Header 全部丢弃。
3. 记录外部响应状态、Content-Type 和耗时，不记录原始响应体。
4. 记录超时/连接失败类型和耗时，不记录异常原文。
5. 继续写入现有日志文件，不新增依赖、配置开关或远端可观测基础设施。
