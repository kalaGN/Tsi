# 模型日志可读格式需求

## 状态

已实现（2026-08-12）。用户已确认以“文件供人阅读、HTTP stderr 供机器采集”的方式重构日志展示。

## 背景

当前 `logs/model-calls.log` 与 stderr 共用单行 JSON Formatter。虽然字段稳定且便于程序解析，但完整请求体、工具参数和工具结果被压缩在单行中，中文正文和多轮消息难以直接阅读。TUI 已关闭 stderr 输出，因此本地文件是 TUI 排障的主要入口。

## 目标

- `logs/model-calls.log` 改为中文、多行、分块的人类可读格式。
- 每个事件继续保留时间、事件类型、request ID 以及适用的 call ID、Provider、模型、状态、耗时和长度。
- JSON 请求体、工具参数和工具结果在可解析时使用 UTF-8 缩进展示；普通文本保持原始换行。
- HTTP stderr 继续输出现有单行 JSON，保持机器采集兼容。
- TUI 继续只写文件，不向 stderr 输出。

## 范围

覆盖现有八类事件：

- `llm_request`
- `llm_response`
- `llm_http_request`
- `llm_http_response`
- `llm_http_error`
- `llm_tool_call`
- `llm_tool_result`
- `llm_tool_approval`

## 非目标

- 不改变事件产生位置、字段白名单、request ID 或 call ID。
- 不改变模型请求、工具执行、HTTP API、错误映射或日志轮转参数。
- 不新增依赖、远程日志系统、日志查询命令、指标或 Trace。
- 不记录真实 Authorization、API Key、Provider 原始响应体或异常堆栈。

## 格式要求

- 时间使用 `Asia/Shanghai`，格式包含毫秒和 `+08:00` 偏移。
- 事件使用中文名称；内部事件字段仍使用稳定英文 key。
- 每个事件以 80 个 `=` 字符结束，事件之间具有清晰边界。
- 内容区使用 `【名称】` 标题；多行正文不得转义为 `\n`。
- 可解析的 JSON 对象、数组或 JSON 字符串使用 `ensure_ascii=False` 和两空格缩进。
- 无法解析为 JSON 的工具参数或结果按原文展示，日志格式化不得影响业务调用。

## 安全与兼容边界

- 文件和 stderr 复用同一份白名单事件数据，不重新读取环境变量或上游对象。
- HTTP Header 继续由日志层使用固定脱敏值构造。
- stderr 保持一事件一行 JSON；只有滚动文件 Handler 使用人类可读 Formatter。
- TUI 文件创建失败时继续静默放弃日志，不恢复 stderr，避免污染全屏界面。

## 验收标准

1. 文件中的模型请求、HTTP 请求、工具调用和工具结果均按中文分块格式展示。
2. 文件时间为北京时间，包含毫秒和 `+08:00`。
3. 文件中的 JSON 内容使用中文不转义的两空格缩进格式。
4. 普通模型输入输出保持原始换行。
5. HTTP stderr 仍是字段集合不变的单行 JSON。
6. TUI 模式仍没有 StreamHandler，日志只进入文件。
7. 轮转、文件失败隔离、事件白名单和脱敏测试继续通过。
8. 项目全量测试、语法检查、依赖检查和差异检查通过。

## 项目结构与编码约束

- Formatter 实现位于 `app/observability/model_logging.py`。
- 回归测试位于 `tests/test_model_logging.py` 和 `tests/test_tui.py`。
- 当前项目使用 Python 3.11、标准库 `logging/json/zoneinfo`；不新增第三方依赖。
- 新 Formatter 只负责展示，不改变事件生产函数及其安全字段白名单。
