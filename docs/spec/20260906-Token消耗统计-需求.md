# Token 消耗统计需求

状态：已完成（2026-09-06）
创建日期：2026-09-06

## 1. 背景

当前 DeepSeek 和阿里云 Provider 都使用流式协议，但统一 `ModelStep`、`ChatResult`、TUI 和模型日志没有暴露 Token usage。DeepSeek 流解析器会忽略携带 usage 的结束 Chunk，阿里云解析器也没有读取 `response.completed.response.usage`。当一次用户请求包含多轮工具调用时，项目无法得知这次请求实际触发的所有上游模型步骤共消耗多少 Token。

这与尚未实现的“TUI 上下文占比”不是同一指标：上下文占比描述下一次请求相对模型窗口的大小，Token 消耗描述上游已实际处理和生成的计量结果。本需求只处理后者，不用 usage 反推上下文窗口占比。

协议依据：

- [DeepSeek Chat Completions API](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion)：流式请求可使用 `stream_options.include_usage` 获取结束 usage Chunk。
- [阿里云 OpenAI 兼容 Responses API](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses)：`response.completed` 的完整 Response 包含 `usage.input_tokens`、`usage.output_tokens` 和 `usage.total_tokens`。

## 2. 目标

- 读取两家上游实际返回的输入、输出和总 Token 数，不使用本地字符估算冒充真实统计。
- 一次用户请求发生多个模型步骤时，累加所有步骤的 usage，得到本轮真实总消耗。
- TUI 在成功回答和耗时信息后展示本轮输入、输出和总 Token。
- 模型日志按步骤记录 usage，并继续使用同一 `request_id`，使成功、工具循环和后续失败场景均可追踪实际消耗。
- 保持 HTTP `/chat` 的 `{"output_text":"..."}` 成功响应和现有错误映射不变。

## 3. 当前假设

1. “Token 消耗统计”指上游返回的 `input_tokens`、`output_tokens`、`total_tokens`，不是本地估算、上下文窗口占比或费用。
2. 工具循环中每次 `Turn.next()` 都是独立计量的模型请求；本轮统计必须包含中间工具决策步骤和最终回答步骤。
3. 第一版只在 TUI 展示成功完成的一轮总消耗；不展示或持久化跨轮、跨进程的会话累计值。
4. 每个已经成功解析 usage 的模型步骤立即写日志；如果后续步骤失败，已经产生的 usage 记录仍保留。
5. usage 缺失时不让原本合法的模型回答失败，统一结果中的统计标记为不可用；若上游显式返回 usage 但类型、范围或求和关系非法，则按无效上游响应处理。
6. 缓存 Token、推理 Token、图片 Token等 Provider 扩展明细暂不展示；它们已包含在上游总量时不重复相加。

## 5. 项目结构与职责

- `app/services/llm/contracts.py`：定义 Provider 中立的不可变 Token usage 值对象，并让单个 `ModelStep` 携带该步骤 usage。
- `app/services/llm/deepseek.py`：请求并解析 DeepSeek 流式 usage。
- `app/services/llm/aliyun.py`：解析阿里云 completed Response usage。
- `app/runtime/tool_loop.py`：按模型步骤记录并累加 usage，不让 TUI 理解 Provider 私有字段。
- `app/runtime/chat.py`：在 `ChatResult` 中返回本轮聚合 usage，同时保持 HTTP Router DTO 不变。
- `app/observability/model_logging.py`：增加稳定的逐步骤 Token usage 日志事件。
- `app/tui/application.py`：仅消费统一结果并展示本轮统计。
- `tests/`：覆盖协议解析、聚合、缺失、非法结构、日志和 TUI 展示。

## 6. 统一契约与代码风格

Provider 私有结构统一转换为不可变值对象：

```python
@dataclass(frozen=True)
class TokenUsage:
    input_tokens: int
    output_tokens: int
    total_tokens: int

    def __add__(self, other: "TokenUsage") -> "TokenUsage":
        ...
```

- 字段必须是非负整数，`bool` 不视为整数。
- `total_tokens` 必须等于 `input_tokens + output_tokens`。
- 聚合逻辑位于 Runtime/契约层，不散落到 TUI 或具体 Provider。
- 只为 usage Chunk 的兼容行为、逐步骤累计和失败保留日志增加必要注释。

## 7. Provider 行为

### 7.1 DeepSeek

- 流式请求增加 `"stream_options":{"include_usage":true}`。
- 接受结束前最多一个 usage 对象；普通 Chunk 中缺失或为 `null` 的 usage 不计数。
- 同时兼容官方描述中的空 `choices` usage Chunk，不把它当作文本事件。
- `[DONE]` 前解析得到的 usage 进入当前 `ModelStep`。

### 7.2 阿里云

- 从 `response.completed.response.usage` 解析三个统一字段。
- 文本步骤和工具调用步骤都读取 usage。
- 其他 Provider 扩展字段不进入统一契约，不改变现有文本及工具结构校验。

### 7.3 缺失与非法 usage

- 完整响应没有 usage：模型结果仍成功，统一 usage 为 `None`，TUI 显示“Token：不可用”。
- usage 存在但字段缺失、为负数、为布尔值/小数/字符串，或总数不等于输入加输出：返回现有 `invalid_response`。
- 不根据输入输出文本自行估算并混入真实统计。

## 8. 工具循环与展示

一个用户请求可能产生：

```text
模型步骤 1（请求工具） usage=100/20/120
模型步骤 2（请求工具） usage=180/15/195
模型步骤 3（最终回答） usage=240/60/300
本轮合计                         520/95/615
```

- Tool Loop 每收到一个合法 `ModelStep` 就累加 usage。
- 每个有效步骤立即写 `llm_token_usage` 日志，字段包含 `request_id`、从 1 开始的 `step_number` 和三项 Token 数。
- TUI 成功完成后在耗时附近写一条有限系统消息：`Token：输入 520 | 输出 95 | 合计 615`。
- usage 不可用时显示 `Token：不可用`；失败或取消不在 TUI 猜测本轮合计，已产生的逐步骤日志仍保留。
- 不把 Token 提示写进 `ChatSession.messages`，因此不会进入后续模型上下文或会话 JSON。

## 9. 可观测性问题

本功能应直接回答：

1. 一次用户请求共消耗多少输入、输出和总 Token？按 `request_id` 汇总步骤日志，成功时也可读取 `ChatResult.token_usage`。
2. Token 主要消耗在哪个工具循环步骤？比较同一请求各 `step_number`。
3. 后续模型步骤失败前是否已经产生计量？此前成功解析的 `llm_token_usage` 事件仍存在。
4. 某 Provider 没有返回 usage，还是返回了非法 usage？缺失按不可用处理，非法按现有无效响应错误处理。

## 10. 测试策略

- 契约单元测试：非负整数、布尔值拒绝、总数一致和加法聚合。
- DeepSeek 测试：请求参数、usage-only Chunk、普通 Chunk null、缺失、重复和非法 usage。
- 阿里云测试：文本、工具步骤、缺失和非法 completed usage。
- Tool Loop 测试：单步、多工具步骤累计、部分步骤缺失、逐步日志以及后续失败时日志保留。
- Runtime/HTTP 测试：`ChatResult` 带统一 usage，`/chat` 仍只返回 `output_text`。
- TUI headless 测试：成功、不可用、失败和取消时的展示边界。
- 所有 Provider 测试使用 MockTransport，不访问真实付费接口。

## 11. 边界

### 始终执行

- 使用 Provider 返回的真实 usage，并在 Provider 边界严格验证。
- 工具循环按所有模型步骤累计，不能只取最终步骤。
- 保留 request ID 关联，不记录 API Key、Authorization 或新增正文。
- 同步更新相关 Spec、设计、任务、README 和 Knowledge。

### 实施前需确认

- 是否将 usage 加入 HTTP 公开响应。
- 是否持久化会话累计、增加费用换算、缓存/推理 Token 明细或预算告警。
- 是否用本地 tokenizer/估算值填补 Provider 缺失数据。

### 禁止

- 修改 `/chat` 当前公开响应契约。
- 把多个模型步骤中的累计输入 Token误当作“唯一上下文大小”或进行去重推算。
- 使用硬编码价格计算费用；模型价格属于易变外部配置。
- 因统计功能调用额外模型请求或真实生产接口。

## 12. 非目标

- 不实现上下文占比、上下文裁剪、摘要或阻止发送。
- 不实现跨会话/跨进程累计、日报、图表、配额或成本账单。
- 不调整 Session schema；不把统计写入对话历史。
- 不暴露 reasoning、缓存等 Provider 私有明细。
- 不增加 Metrics、Trace、远程采集或第三方依赖。

## 13. 验收标准

1. DeepSeek 和阿里云的每个模型步骤都能从官方流式结构提取合法 usage。
2. 工具循环有多个模型步骤时，本轮 Token 等于所有已完成步骤的输入、输出和总量之和。
3. TUI 成功回答后显示本轮 Token；缺失 usage 显示不可用，失败和取消不显示伪造合计。
4. 每个有 usage 的模型步骤产生一条可按 request ID 查询的日志，后续失败不删除既有记录。
5. `/chat` 继续只返回 `{"output_text":"..."}`，错误状态与正文保持不变。
6. 不修改 Session schema，不新增第三方依赖，不调用真实模型。
7. 日志脱敏、TUI 流式输出、工具调用、历史恢复、耗时和现有交互均不回归。
8. 定向测试、全量测试、语法检查、依赖检查和 `git diff --check` 全部通过。

## 14. 已确认项

1. 是否确认统计上游真实 usage，并在缺失时显示“不可用”，不使用本地估算？建议：是。
2. 是否确认工具循环的所有模型步骤都计入本轮总消耗？建议：是。
3. 是否确认第一版只展示本轮消耗并记录逐步骤日志，不持久化会话累计？建议：是。
4. 是否确认 `/chat` 公开响应保持不变，仅 TUI 展示 Token？建议：是。

确认结果：2026-09-06 用户回复“继续”，四项均采用建议方案。
